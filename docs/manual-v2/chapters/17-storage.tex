\chapter{Persistent Storage}
\label{chap:storage}

CharlotteOS treats storage as a layered stack of userspace services, each
speaking a well-defined protocol through endpoint IPC. The block driver,
object store, and filesystem services run in userspace. The kernel still
participates through capability, memory-mapping, physical-address, interrupt,
and PCI/MSI-X setup paths.

\section{NVMe block driver}

The NVMe driver is a userspace EL0 prototype implementing the subset needed for
QEMU bring-up: controller and namespace identification, queue creation, and
basic read, write, and flush operations. NVMe 1.4 compliance has not been
established. It receives an \texttt{MmioRegion} capability covering the controller's
BAR0 register window, an \texttt{Interrupt} capability for I/O
completion signalling, and a \texttt{DmaDomain} capability bound to the
controller's PCI requester ID. Queue and data memory are mapped with
\texttt{dma\_map}; the driver receives contiguous IOVAs rather than physical
addresses. The kernel pins the backing frames and removes each translation
with a synchronous SMMU invalidation before unpinning.

\subsection{Initialization}

The driver follows the standard NVMe initialization sequence:

\begin{enumerate}
    \item Controller reset: disable CC.EN, wait for CSTS.RDY = 0.
    \item Admin queue setup: allocate physically contiguous memory for the
        Admin Submission Queue (ASQ, 32 entries) and Admin Completion Queue
        (ACQ, 32 entries). Write AQA, ASQ, and ACQ registers. Enable the
        controller and wait for CSTS.RDY = 1.
    \item Identify controller: submit an Identify command (CNS=1) through
        the admin SQ. Read capabilities, version, and supported features.
    \item Set Features (Number of Queues): declare how many I/O queue
        pairs the driver intends to use. QEMU's NVMe controller requires this
        before accepting I/O queue creation commands.
    \item Identify namespace: submit an Identify command (CNS=0, NSID=1)
        to read the namespace size (NSZE) and the active LBA format (FLBAS),
        which determines the block size.
    \item Create I/O Completion Queue: allocate memory, submit a Create
        I/O CQ admin command. The CDW11 register must set bit 0 (PC =
        Physically Contiguous) to 1. The NVMe
        specification and enforced by QEMU's device model.
    \item Create I/O Submission Queue: allocate memory, submit a Create
        I/O SQ admin command, associating it with the I/O CQ created in the
        previous step.
\end{enumerate}

After initialization the driver registers \texttt{"blk0"} with the name service
and enters its main loop, blocking on \texttt{cq\_wait} for endpoint messages
and I/O completions.

\subsection{I/O path}

\textbf{OP\_READ} receives a BorrowWrite memory attachment from the caller. The
driver maps it into the controller's DMA domain, builds a PRP chain from the
returned IOVA range, and submits an NVM Read. On completion it unmaps the DMA
translation, replies, and lets the kernel revoke the borrow and return the filled
buffer to the caller.

\textbf{OP\_WRITE} receives a Move memory attachment, maps it for DMA, builds the
PRP chain, and submits an NVM Write. On completion the driver removes the mapping
and replies; the moved buffer is consumed.

\textbf{OP\_FLUSH} submits an NVM Flush command to ensure all previously
written data reaches durable media before replying.

\subsection{Lessons from bringup}

The NVMe driver exposed several non-obvious requirements:

\begin{itemize}
    \item CDW11 bit 0 (PC) must be 1: QEMU's NVMe device model
        requires physically contiguous queues. Without this bit, the Create
        I/O CQ command returns status 0x4002 regardless of all other
        parameters.
    \item SQE layout is exacting: the Command Identifier occupies
        bits 31:16 of DW0, the opcode occupies bits 7:0. The NSID shares
        DW0's high bits with DW0 in the first u64. PRP1 is at byte offset
        24, CDW10-11 at byte offset 40. Getting any of these wrong produces
        silent failures.
    \item Doorbell stride must be derived from CAP.DSTRD: on QEMU
        this is 0 (stride = 4 bytes), but the architecture supports strides
        up to $4 \ll 15$ bytes.
    \item MMIO mapping must cover the doorbell region: the NVMe
        controller registers occupy offsets 0x0000--0x003F within BAR0, but
        doorbell registers start at offset 0x1000. A single-page MMIO grant
        is insufficient; at least two pages are needed.
    \item On TCG, \texttt{cq\_wait} is required for VM exits: a
        pure spin-loop prevents QEMU from processing I/O because the guest
        never yields. The driver must block on \texttt{cq\_wait} to let the
        host process NVMe commands.
\end{itemize}

\section{Block device protocol}

The block protocol (\texttt{charlotte-protocol-block}) is a minimal
\texttt{no\_std} crate defining the endpoint IPC interface between block
device consumers and drivers:

\begin{longtable}{|c|l|p{7cm}|}
\hline
\textbf{Opcode} & \textbf{Name} & \textbf{Description} \\
\hline
1 & OP\_INFO & Query block size and total block count. Scalar call/reply. \\
2 & OP\_READ & Read blocks into a BorrowWrite memory object. \\
3 & OP\_WRITE & Write blocks from a Move memory object. \\
4 & OP\_FLUSH & Flush write cache to durable media. \\
5 & OP\_TRIM & Discard a block range (optional). \\
\hline
\end{longtable}

The protocol is device-independent: consumers speak
\texttt{OP\_READ}/\texttt{OP\_WRITE} without knowing the underlying hardware.
Three userspace implementations are present. NVMe is exercised on AArch64 and
x86-64; x86-64 additionally runs AHCI and virtio-blk implementations through
the same protocol. The QEMU matrix validates identify/capacity discovery,
bounded read and write requests, flush completion, controller timeouts, and
the persistent object-store/Raft restart path. On x86-64 all three transports
are tested behind VT-d or AMD-Vi DMA domains. Ramdisk and network block drivers
would still require separate implementations.

\section{Object store}

The persistent object-store prototype (\texttt{charlotte-protocol-objstore})
provides dynamically sized blob storage on top of a block device. Ordinary objects
receive monotonically increasing 64-bit IDs; service-owned objects can use
stable IDs through \texttt{OP\_CREATE\_AT}. Stable IDs let a replacement Raft
process reopen state derived from its cluster and node identity.

\subsection{On-disk layout}

\begin{verbatim}
LBA 0--1:  checksummed superblock slots
next:      device-sized allocation bitmap
next:      two device-scaled directory banks:
             id | flags | generation | header_lba |
             header_blocks | crc32
data:      object headers and up to 16 data extents per object
\end{verbatim}

\subsection{Current durability boundary}

Both superblock reads must finish successfully before their absence or
validity can select mounting or formatting. Allocation, IPC, device or mapping
rejection fails startup; unreadable metadata is not evidence of a blank disk.
Only two successfully read zero-filled superblock slots permit first-boot
formatting. Retired format tags reject even alongside a current copy. A valid
current copy can recover a blank or corrupt peer; nonblank metadata with no
current copy and incompatible layouts fail without reformatting.

The store publishes explicit Starting, Serving, Draining and Failed states.
Serving follows mount and endpoint registration; kernel local readiness
acquires and revalidates that milestone. Diagnostic stages and ordinary I/O
errors are separate. The marker records startup completion; later I/O can still fail.
First-failure diagnostics retain state, operation, LBA/count, phase and
available status/result without retry. See
\repofile|docs/reports/audits/2026-10-12-security-object-store-readiness.md|.

Each object header is versioned and carries explicit header length and block
count, object generation, exact and allocated data lengths, data offset,
extent information, and a mandatory FNV-1a content hash. The fixed header
rejects extension lengths rather than filling absent fields. It records up to 16
extents, so fragmented free space does not require one large contiguous run.

Replacement is copy-on-write. New data, header, and allocation state are
flushed before the directory locator changes, and the old allocation is freed
afterward. Mount reconstructs the bitmap from validated reachable headers,
reclaiming pre-commit allocations. Whole-object transfers use multi-page
memory objects and are divided into block requests of at most 512 KiB. Objects
and files can be larger than a single request. The current service API's
32-bit length limits an individual object to 4 GiB and available disk space.
Directory records are checksummed and mirrored. Each update goes to the
generation-selected bank, and mount chooses the newest valid copy per record;
versioned tombstones prevent deleted records from reappearing. This recovers
from one torn directory-sector write. Full device-level sudden-power-loss
guarantees still depend on truthful flush/FUA behavior. FNV-1a detects
accidental corruption, but is not cryptographic authentication.

\subsection{Operations}

\begin{itemize}
    \item \textbf{CREATE}: allocate a directory slot, return a new object ID.
    \item \textbf{CREATE\_AT}: create a caller-selected stable object ID, or
        report that it already exists.
    \item \textbf{WRITE}: replace the object's content. The caller moves a
        suitably sized memory object; the store writes it in bounded chunks.
    \item \textbf{SET\_SIZE}: set the exact byte length consumed by the next
        whole-object write.
    \item \textbf{READ}: return the object's data as a moved memory object.
    \item \textbf{DELETE}: mark the directory entry as free, return the
        extent blocks to the free bitmap.
    \item \textbf{FLUSH}: flush the underlying block device.
\end{itemize}

\subsection{Object authority}

The store authenticates each sender through the kernel IPC envelope and records
the creating principal in the object header. Ordinary objects are private to
that principal and the kernel, including across service replacement. Shared-read
objects permit other authenticated readers while retaining owner-only mutation.
Reserved artifact and executable namespaces are publicly readable but mutable
only by the kernel and the signed \texttt{clusterctl} administration service.
A persisted operator table admits at most 64 principal/range grants for read or
write access; grants cannot extend the reserved mutation allowlist. Node/operator
enrollment and management-channel authentication remain separate requirements.

Authorization and data access consume one validated locator/header snapshot.
Missing objects return NotFound; metadata I/O or validation failure returns an
error rather than adopting public ownership defaults. Automatic creation searches
for an unused positive scalar ID with a directory-sized bound, preserving
explicitly created objects. Mount rejects duplicate live IDs. Current format
v4 uses COBJSTR4 superblocks and fixed 384-byte CCOBJHD4 headers with explicit
nonzero owners, known attributes and zero reserved/unused fields. Host-staged
artifacts use the kernel principal. Owner-zero metadata and older stores reject
before mutation; deployed format changes will require explicit migration.
See \repofile|docs/reference/security-remediation.md| for current disposition
and validation limits.

\subsection{The initial service-artifact store}

The host build produces an architecture-qualified service bundle and blesses
every ELF according to
\repofile|crates/catten-services/artifact-policy.tsv|. AArch64 embeds naming,
storage, UART, observation and grant mediation, plus the boot entropy/network
driver images needed to prepare grants before starting storage. The exact sets
are listed in \autoref{chap:cluster-vision} and
\repofile|crates/catten/src/service/store.rs|;
\repofile|scripts/make-nvme-image.py| writes the remaining
services into an initial version-4 object-store image. The QEMU x86-64 runner
can use the same host-preseeded model.

The x86-64 kernel also carries an immutable signed installation bundle for the
blank-disk appliance path. Once NVMe and the object store are available, it
checks the stable object ID for every bundled logical name. A valid stored
artifact is retained, including a newer deployed version; a missing artifact
or one that fails identity and signature verification is replaced from the
bundle. The installer flushes the store before dependent services start, so
the operation is idempotent across reboot. Services are subsequently resolved
by logical name, read through the object-store protocol, identity-checked, and
cached for the boot. The ordinary loader independently enforces ELF and
signature policy before mapping.

The signature record is CLS2, an identity-bearing ELF note. Besides signing
the complete bytes, it binds the logical service name, artifact class, release
and rollback counter, policy flags, signing-key id, and an optional provenance
digest. Consequently a validly signed \texttt{dns} ELF cannot occupy the
\texttt{raft} slot. A deployment generation also carries the complete ELF
SHA-256, preventing an object replaced under the same logical name from
changing already-committed code.

For preseeded QEMU images, the runner fingerprints the whole blessed bundle.
It rebuilds an instance's initial NVMe image when that fingerprint changes,
while \texttt{--reuse-storage} deliberately retains an older store and emits a
staleness warning. \texttt{--fresh-storage} always recreates it. The image
producer refuses an object-id collision rather than silently replacing an
earlier service. The x86-64 options \texttt{--blank-storage} and
\texttt{--build-only} instead support guest-side installation and appliance
packaging without constructing a preseeded store.

\section{Managed object storage through S3}

The local \texttt{objstore} and the S3 client service solve different
problems. The local store is part of node bootstrap and supplies service
artifacts, Raft persistence, and the native filesystem without depending on a
working network or external credentials. The \texttt{s3} service is an
application-facing compatibility adapter for centrally managed object stores.
It runs above TCP/IP and, when configured, verified TLS; it is described in
\autoref{sec:s3-service}.

An S3 service profile narrows authority to one endpoint, bucket, key prefix,
credential identity, optional Dell EMC ECS namespace, and operation mask.
Applications receive only the profile's endpoint capability and transfer
object data as owned memory chunks. This makes external object storage usable
without handing each application general socket access or raw S3 credentials.

Static provisioning and operational pickup both supply the complete immutable
\texttt{CHS3PF1} profile through read-only launch memory. The service rejects
missing or malformed profiles; it no longer reads per-field manifest aliases
or synthesizes region and port defaults. The shared profile codec is the single
validation boundary. Encoded profiles and the service's local profile snapshot
use erasing owners. The original read-only launch memory follows the kernel's
separate teardown policy.

RustFS is the current integration fixture. Dell EMC ECS is an intended managed
store and the adapter can emit its namespace header, but it has not yet been
qualified against an ECS installation. The cluster deployment agent can use a
separately provisioned S3 connector as an artifact source: it reads the opaque
key from a signed deployment descriptor, streams the ELF, checks its pinned
SHA-256 and name-bound CLS2 signature, and transfers both ELF and descriptor to
the scoped kernel launch gate. Credentials, endpoint, bucket, prefix, and TLS
identity remain outside both descriptor and application. Bootstrap services
still come from the local store; the node can boot without central S3. Caching,
availability policy, credential rotation, and an end-to-end managed-store
qualification remain operational work.

\section{Raft persistence}

The Raft service selects memory (\texttt{storage=0}, or omitted) or required
persistence (\texttt{storage=2}); retired mode 1 and malformed policy values
reject. Required mode waits for \texttt{"obj"} through the name service.
One jointly validated two-object pair holds \texttt{CRFTSTA4}
term/vote/join-admission state and \texttt{CRFTLOG4} snapshot/log state.
Only two absent records authorize initialization; existing empty, incomplete,
corrupt or unsupported records reject without reset or a memory fallback.
Older decoders and split-store migration are removed. Each mutation writes
the complete object and flushes the underlying NVMe device before returning.
Snapshot bytes and the retained log suffix share one replacement point in the
log object. The two-object pair has no cross-object atomicity guarantee.
Future deployed-store changes
require an explicit version-directed migration. See
\path{docs/reference/raft-persistence.md}.

The focused local election fixture runs two in-process Raft members with memory
stores, keeping consensus behavior testable on a multicore machine without
NVMe. We chose its peer count for the fixture; Raft is not limited to that count.
A separate storage test starts a single voter with required persistence,
records its elected term, tears down that process, restarts the same identity,
and requires the new election term to be greater. A repeated term 1 would
fail, so the test distinguishes recovery from a fresh in-memory start.

Launch configuration (node identity, peers, election timeout, cluster name,
and storage policy) remains in the supervisor-provided manifest. The
persistent objects hold Raft protocol state, log entries, and snapshots.
Cross-machine catalog replication is provided separately by the \texttt{dns}
state machine described in \autoref{chap:consensus} and
\autoref{chap:cluster-vision}; this generic Raft persistence test
remains a single-voter restart test.

\section{Native filesystem}

The filesystem (\texttt{charlotte-protocol-fs}) builds hierarchical naming on
top of the object store. Directories and files are stored as objects; the root
directory is a fixed object ID (100).

\subsection{Directory encoding}

Each directory object stores entries as a packed sequence:

\begin{verbatim}
[name_len: u32 LE][name: UTF-8]
[file_id: u64 LE][flags: u32 LE][size: u64 LE]
\end{verbatim}

A \texttt{name\_len = 0} marker terminates the list. Flags distinguish
directories (bit 0 set) from files (bit 0 clear).

\subsection{Path resolution}

Paths are walked client-side by chaining \texttt{OP\_LOOKUP} calls. The
filesystem service does not understand path strings; it resolves only
single-component lookups within a given directory. This keeps the filesystem
protocol minimal: six operations (LOOKUP, CREATE, READ, WRITE, DELETE, LIST)
plus FLUSH.

\subsection{Host inspection}

A Python tool (\repofile|scripts/fs-inspect.py|) reads the raw disk image and
walks the object store and filesystem on-disk structures. It understands both
v4 directory banks and multi-extent headers, selects the newest valid directory
record, checks CRCs and allocation overlap, compares reachable blocks with the
bitmap, and verifies object contents against their FNV-1a hashes. It provides
tree, dump, raw, cat, object-list, metadata, information, and format commands,
enabling post-mortem debugging without booting CharlotteOS:

\begin{verbatim}
scripts/fs-inspect.py <image> info
scripts/fs-inspect.py <image> objects
scripts/fs-inspect.py <image> metadata
scripts/fs-inspect.py <image> metadata OBJECT_ID
scripts/fs-inspect.py <image> metadata /path/to/file
scripts/fs-inspect.py <image> tree
scripts/fs-inspect.py <image> cat /raft/state
\end{verbatim}

Metadata output includes numeric and symbolic object/filesystem flags,
generation, header location, logical and allocated lengths, integrity hash, and
every extent. Filesystem flag bits remain visible; unsupported object-store flags reject validation. The \texttt{format} command
creates a blank v4 store and destructively replaces the image contents.

\section{Isolation and durability limits}

\begin{enumerate}
    \item Storage policy lives in userspace: a bug in a block
        driver, the object store, or the filesystem corrupts that service's
        address space. The kernel grants MMIO and interrupts; the storage
        implementation stays in userspace.

    \item Device-independent protocol: the object store and filesystem use
        one block protocol over the implemented NVMe, AHCI, and virtio-blk
        userspace drivers. Further backends can implement the same protocol
        without moving storage policy into the kernel.

    \item Crash-safety mechanism under development: process-restart
        persistence is boot-validated. Copy-on-write object replacement and
        mirrored directory records recover from one torn directory-record
        write. Broader power-loss guarantees still require validation of
        device atomicity and truthful flush/FUA ordering.

    \item Capability-based access: a client that holds a connection to
        \texttt{"blk0"} can read and write blocks. A client that does not hold
        that connection cannot. There is no ambient filesystem namespace to
        escape.

    \item Host-inspectable: the included Python inspector reads the raw
        disk image and reports its documented object and filesystem structures.
\end{enumerate}
