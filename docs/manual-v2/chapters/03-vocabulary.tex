\chapter{Vocabulary}
\label{chap:vocabulary}

This chapter defines specific terms used in this manual.

\section{Protection domain}

A \textbf{protection domain} is an address space and authority boundary. It owns:

\begin{itemize}
    \item A capability table.
    \item Memory mappings.
    \item One or more execution contexts (threads).
    \item Resource accounting.
    \item Failure and teardown state.
\end{itemize}

A \emph{process} implements a protection domain. This manual uses the broader
term when discussing isolation and authority rather than a particular process.

\section{Execution context}

An \textbf{execution context} is a kernel-scheduled thread. It may have:

\begin{itemize}
    \item Logical processor (LP) affinity.
    \item Priority or scheduling class.
    \item A current protection domain.
    \item A wait state.
    \item An associated userspace executor.
\end{itemize}

\section{Logical processor (LP)}

A \textbf{logical processor} is CharlotteOS' representation of a schedulable
hardware execution context, typically one CPU core or one hyperthread.

An LP is not a shard (in the Sitas sense). A typical mapping is:

\begin{center}
\begin{tikzpicture}[
    box/.style={draw, rounded corners, align=center, inner sep=5pt},
]
    \node[box] (shard) {one Sitas shard};
    \node[box, right=0.8cm of shard] (thread) {one LP-affine\\userspace thread};
    \node[box, right=0.8cm of thread] (cpu) {normally one\\logical CPU};
    \draw[<->] (shard) -- (thread);
    \draw[<->] (thread) -- (cpu);
\end{tikzpicture}
\end{center}

The architecture makes this distinction so that CPU hotplug, oversubscription,
migration, asymmetric CPUs, and multiple sharded processes remain possible.

\section{Sitas shard}

A \textbf{shard} is a userspace ownership and execution domain:

\begin{itemize}
    \item One executor runs its tasks.
    \item At most one task at a time mutates shard-owned state.
    \item Cross-shard access occurs through typed messages carrying owned values.
    \item Placement is explicit and remains separate from the shard's identity.
\end{itemize}

\section{Capability}

A \textbf{capability} is an unforgeable reference to a kernel object, carrying
rights. It answers the question: ``May I perform this operation?''

Capabilities are scoped to a protection domain's capability table. A process
cannot fabricate a capability, because the kernel issues one through an authorized
creation, bootstrap, or delegation operation.

\section{Endpoint}

An \textbf{endpoint} is a bounded server-side IPC receive object. It has:

\begin{itemize}
    \item An owning protection domain.
    \item A queue capacity.
    \item A protocol/interface identity.
    \item Receive rights.
    \item Lifecycle and closure state.
\end{itemize}

\section{Connection capability}

A \textbf{connection capability} is a client-side authority to send or call an
endpoint. A name service resolves a name and conditionally returns a connection
capability associated with that name.

\section{Message}

A \textbf{message} is a kernel-validated IPC envelope consisting of:

\begin{itemize}
    \item Interface or protocol identifier.
    \item Opcode.
    \item Flags.
    \item Inline scalar words.
    \item Zero or more memory-object attachments.
    \item Zero or more delegated capability attachments.
    \item Optional reply authority.
\end{itemize}

The kernel understands the envelope structure while arbitrary Rust types remain a
userspace concern.

\section{Reply token}

A \textbf{reply token} is one-shot authority to complete a blocking or deferred
call. It is:

\begin{itemize}
    \item Created by the kernel.
    \item Bound to the caller's pending call.
    \item Consumable exactly once.
    \item Invalidated by cancellation, caller death, or endpoint teardown.
    \item Owned by the receiving service, and the current userspace API does not
        provide general reply-token delegation.
\end{itemize}

\section{Resource capability}

A \textbf{resource capability} authorizes operations on a kernel-managed object
such as a memory object, endpoint, connection, interrupt, MMIO region, DMA domain,
or a completion for an operation or timer. The unified namespace also holds
mailbox and system-observer authority. Completion queue (CQ) identifiers select
domain-local queues and are not a separate capability family.

\section{Operation and completion queue}

An \textbf{operation} is submitted work whose progress may depend on the kernel,
hardware, or a privileged service.

A \textbf{completion queue (CQ)} brings operation results together for a shard
or process. A thread can wait on it with \texttt{checked CQ wait}, and terminal
results are not lost.

\section{Notification}

A \textbf{notification} means: ``State may have changed, so inspect the corresponding
object or queue.'' Several notifications may be combined into one, but the
notification is itself not a result.

\section{Rust Waker}

A Rust \texttt{Waker} means: ``Poll this userspace future again.'' It is a
userspace scheduling hint, is not a kernel completion record, and it should not
cross the ABI directly.

\section{Resource and cleanup terms}

The implementation notes use a few terms with specific meanings:

\begin{description}
    \item[Admission] Checking and reserving capacity before accepting work.
        Passing an authority check does not mean that capacity is available.
    \item[Backing] The memory allocated for an object's data or bookkeeping,
        as distinct from the handle used to refer to it.
    \item[Principal] The identity used for authorization and resource accounting.
        It is distinct from a process or thread number that can later be reused.
    \item[Fencing] Blocking particular operations to protect a resource. A
        generation check can reject a stale request without granting authority
        over its replacement. A fence alone does not prove cleanup has finished.
    \item[Quiescence] A state in which the relevant CPU or device activity has
        stopped. This must be confirmed before its resources are reused or freed.
        A deadline alone does not provide that confirmation.
    \item[Retention] Keeping a resource and its owner when they cannot yet be
        released safely. This does not itself prove completion or permit retry.
    \item[Inert owner] An owner whose Drop does not automatically release its
        resources. Explicit cleanup must follow the owner's own contract.
    \item[Escrow] Source authority and accounting state set aside during a
        transfer, so the exact original owner can be restored if rollback is
        allowed. Keeping the memory pages alone is not enough.
\end{description}

\section{Distinctions that matter}

Several concepts sound similar but must be kept separate. Confusing them leads to
architectural mistakes.

\begin{center}
\begin{tabular}{|l|l|l|}
\hline
\textbf{Concept} & \textbf{Is} & \textbf{Is not} \\
\hline
Capability & Unforgeable authority to act & An event, a file descriptor, a handle \\
Endpoint & Server-side bounded receive queue & A socket, a pipe, a channel \\
Completion & A result of an async operation & A Waker, a notification \\
Waker & A hint to repoll a future & A kernel completion record \\
Shard & A userspace ownership domain & An LP, a core, a thread \\
LP & A schedulable hardware context & A shard \\
Notification & ``Inspect state'' & A result, a data payload \\
IPC call & Cross-domain service invocation & A kernel operation submission \\
\hline
\end{tabular}
\end{center}

\section{Quick reference: acronyms}

\begin{description}
    \item[ASID] Address Space Identifier. 0 = kernel; $>$0 = user address space.
    \item[CQ] Completion Queue. Shared-memory ring buffer for async operation
        results.
    \item[EL0] Exception Level 0 on AArch64. CharlotteOS also uses
        \texttt{EL0} as an architecture-neutral source and test label for
        userspace execution, including ring 3 on x86-64.
    \item[EL1] Exception Level 1 (AArch64). Kernel execution.
    \item[HHDM] Higher Half Direct Mapping. Linear mapping of all physical memory
        into kernel virtual address space (provided by the Limine bootloader).
    \item[IPI] Inter-Processor Interrupt. Signal from one LP to another.
    \item[LP] Logical Processor. One schedulable hardware execution context.
    \item[MMU] Memory Management Unit. Hardware that enforces page-table
        permissions.
    \item[IOMMU / SMMU] I/O Memory Management Unit. Enforces DMA access
        permissions from devices, analogous to the MMU for CPU access.
\end{description}
