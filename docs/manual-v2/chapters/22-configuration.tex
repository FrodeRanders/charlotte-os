\chapter{Configuration}
\label{chap:configuration}

Configuration expresses the workload and capacity a node is intended to support.
A security limit needs an owner, a unit and an admission rule, but its chosen
capacity also needs an explanation and a way to change it. Resource ceilings
are therefore collected in a typed kernel policy, separate from the allocation
and cleanup code that enforces them.

This chapter describes current configuration mechanisms and how to qualify a
change. The matching operator guide is
\repofile|docs/guides/configuration.md|; the complete resource-policy inventory
and dimensions are in \repofile|docs/reference/resource-policy.md|.

\section{Configuration sources and authority}

The following inputs have different authorities and lifetimes:
\begin{description}
    \item[Management TLS.] A complete signed, encrypted boot resource supplies
        server credentials, client roots, exact operator roles and all eleven
        TLS limits. The kernel verifies it against its selected admission policy
        before publishing trust, then supplies read-only launch profiles to both
        management services. Missing credentials disable network admission.
        Protected installation and authenticated time remain audit gaps.
    \item[Dependency advisory policy.] CI/local validation reads
        \path{.cargo/audit.toml} and the scanner pin in \path{.cargo/audit-version}.
        These configure validation, not a running node. Database contents refresh
        at each invocation; a later advisory can reject the same lockfile.
    \item[Domain TLS entropy.] Startup consumes one \texttt{EntropyConfig}
        containing an owned entropy connection (or explicit architectural-only
        source) and positive request budget. It cannot adopt a borrowed launch
        capability or replace installed source/limits. This is runtime authority
        and observation policy, not a kernel capacity-profile field.
    \item[Kernel resource policy.] Trusted Rust build input selects capacity
        ceilings, ordinary shares and platform reserves. It is compiled into
        the kernel and remains fixed throughout that boot.
    \item[Bootstrap assignments.] The kernel build consumes
        \path{CATTEN_CLUSTER_SERVICES}. Boot runners accept repeatable
        \texttt{-{}-cluster-service [NAME=]IPv4:PORT} assignments. The first
        committed signed ingress policy replaces the bootstrap assignments.
    \item[Trust policy.] The kernel's one prepared boot-trust policy supplies
        launch and grant verification. Capacity configuration cannot install
        keys, grant platform classification or enable production trust.
        Production remains disabled pending protected provisioning and custody.
    \item[Application launch policy.] Signed deployment and kernel admission
        determine per-domain stack/thread limits, executable variants,
        delegated capabilities and protocol-specific launch profiles. An
        application's request does not enlarge a node-wide capacity pool.
    \item[Persistent state.] A storage format tag and committed state are not
        disposable configuration. Changing capacity never authorizes silent
        reformatting, resetting election state or discarding retained charges.
\end{description}

Internal protocol fields, architectural address ranges, page granularity and
hardware register widths are separate structural contracts. Changing their
numbers requires a coordinated implementation and format review. They are not
ordinary operator capacity settings.

\section{Selecting the compile-time resource policy}

The default settings are in
\repofile|crates/catten/src/resource_policy/defaults.rs|. They retain the existing
capacity values. Operators may edit this central file or select an external
profile with \texttt{CATTEN\_RESOURCE\_POLICY}, which must name an existing file
by absolute path. Unset selects the default; empty, relative, missing and
directory paths reject. The file is trusted Rust source and belongs in the
reviewed build inputs, not in an application manifest or upload request.

A profile defines \texttt{POLICY: Policy} in the policy module's scope. It can
start from \texttt{DEFAULT} and override related fields. The checked-in
\repofile|crates/catten/src/resource_policy/larger.rs| demonstrates co-scaling
scratch-node, snapshot-buffer and mapping-node byte/count capacities by one
quarter while retaining their reserve proportions.

\begin{lstlisting}[language=bash]
CATTEN_RESOURCE_POLICY="$PWD/ops/resource-policy.rs" \
  scripts/run-aarch64.sh --security-test --http-test
\end{lstlisting}

The runners pass this environment input through to the kernel build. Cargo
tracks the selected path, its contents and environment selection. Changing or
unsetting the selection rebuilds the kernel; userspace service images do not
need rebuilding for these policy fields. Boot serial output identifies the
selected policy name. Record the exact profile source and kernel artifact
hashes with qualification evidence; the name alone is not an artifact identity.

There is currently no resource-policy boot-module parser, capability, syscall
or live-resizing interface. The compiled policy does not change after charges
exist. Boot-time resource input is a future installation mechanism, not an
implemented fallback for an invalid build profile.

TLS record and certificate capacities are grouped build constants in
\repofiletext|crates/catten-services/src/tls_client.rs|{the shared TLS adapter}.
Each stream owns two
\texttt{16640}-byte record buffers; the verifier admits a complete Certificate
message up to \texttt{16384} bytes. These values are compile-time adjustable,
with record-framing requirements, handshake stack usage and heap grants reviewed
together. Increasing storage does not add intermediate-chain validation.
Driver context layouts and backend erasure flags remain structural build
contracts. Changing these inputs requires rebuilding and qualifying both service
variants; the kernel resource profile does not resize them. See
\repofile|docs/reference/tls-client.md|.

The entropy request deadline is a separate startup API setting in
\texttt{EntropyLimits}. Bundled S3, Kafka and TCP/IP select its central
\texttt{5000} ms default; startup Rust code can supply another positive budget.
No manifest/config-page field or live update is added. Increasing the budget
retains source checkout, pending metadata, output borrow and possible returned
backing longer, so timeout/rejection and pressure need joint qualification.
One original monotonic deadline survives preparation and observation without
replay. This bounds reply observation, not dependency naming or kernel cleanup
latency. Details and exact inputs are in
\repofiletext|docs/reference/tls-client.md|{the TLS configuration reference}.

The shared entropy protocol groups \texttt{BUFFER\_PAGES},
\texttt{BUFFER\_BYTES} and \texttt{MAX\_REQUEST}, currently one 4096-byte page.
These compile-time dimensions control caller allocations and
the driver's private DMA buffer together; descriptor lengths must fit
\texttt{u32}. Rebuild every caller and driver, then qualify maximum sizes,
rejection, retention, cancellation and DMA before changing them. This adds no
boot-resource parser or live resizing. DNS's separate
\texttt{CAPACITY\_NONCE\_TIMEOUT\_MS} groups its 100 ms lookup/fill observation
budget in the capacity-report context. See
\repofiletext|docs/reference/entropy.md|{the entropy configuration reference}.

RNG publication uses the shared platform-service compile-time policy: 1000 ms
admission, 5000 ms accepted-call observation and 10 ms queue-full-only admission
backoff. These are separate phase budgets. Tune all helper consumers and boot
readiness deadlines together in the shared publication module; RNG adds no
per-instance or live override. Its idle request/lifecycle wait is event-only,
without a timer policy.

The hardware-polling policy is separate. The central RNG device limits allow
1000000 completion-index reads per descriptor; the typed constructor requires a
positive bound. This is an iteration ceiling, not milliseconds or permission to
retry. Each confirmed short completion may require another bounded step. The
compile-time queue size is eight; page-rounded ring backing derives from its
geometry, while bounce storage follows the protocol buffer. Larger queues do
not increase outstanding descriptors. Rebuild and qualify layout, CPU cost,
caller deadlines, short completion, timeout/late completion and retained cleanup
together. No boot-resource or live override is added. Exact inputs are in
\repofiletext|docs/reference/entropy.md|{the entropy configuration reference}.

\section{Related limits and tuning consequences}

The policy groups domain/ordinary/total capacities and resource dimensions.
For fixed pools, every ordinary dimension is positive and below the total;
domain dimensions must fit the ordinary pool. A reserve is the difference
between total and ordinary admission, not a guaranteed share for one service.

Examples of settings that require joint review include:
\begin{itemize}
    \item Memory-object size, aggregate domain/principal backing and snapshot
        bytes. One maximum-sized object must fit an ordinary frame snapshot.
        Increasing object size can also increase mapping work and pin lifetime.
    \item Mapping nodes, scratch extents and snapshots. Concurrent preparations,
        live objects and uncertain cleanup all consume admission. Raising the
        live-object target without space for preparation can prevent progress.
    \item Endpoint counts, queue slots, completion queues, connections,
        pending/reply records, capabilities, waiter entries and observer lists.
        One outstanding RPC can consume several of these families together.
        Endpoint backing rounds queue capacity to a power of two.
    \item Lifecycle watches, publication counts and replacement overlap.
        A name-service replacement needs the new watch before disposing the old
        one; service minima must be tested as part of boot qualification.
    \item Unified memory authority and shared payload/namespace/read-borrower
        node bytes/counts. Every overlapping preparation needs two temporary
        nodes, or three for a read loan, including the namespace candidate for
        an already-established namespace. Published and
        retained metadata consumes its original quota until deallocation.
    \item Thread bundles, principal thread metadata, stacks and private tables.
        More runnable domains can encounter any of these ceilings before their
        individual thread limits, including while old generations remain retained.
    \item Requested metadata bytes, allocator overhead, kernel-heap backing and
        physical progress reserves. Independent logical pool totals do not form
        a complete physical-RAM ledger and cannot establish fairness by addition.
\end{itemize}

RAM-derived pools use documented ratios of discovered usable pages, with
checked widened arithmetic. The heap reserve has a RAM divisor, aligned floor
and aligned ceiling. It clamps before alignment rounding, including extreme
reported RAM. The current launch ABI still bounds heap virtual capacity; the
kernel checks policy against that contract and the actual allocator arena.

Capacity changes do not alter sponsorship or cleanup. A move keeps its original
charge, and root retirement, ASID reuse or later platform promotion cannot refund
live backing. Failed physical cleanup retains the original complete owner and
charge. A larger budget never supplies proof of completion or permission to
replay accepted work.

Raft election timing is selected by
\texttt{RaftNodeConfig::timeout\_millis}; native launch supplies 2000 milliseconds
through the DNS \texttt{elect-ms} manifest entry. Initial and subsequent
deadlines derive a jitter window of one configured timeout, rather than a fixed
150 milliseconds. Repeated-election backoff derives from the same timeout, and
deadline/backoff arithmetic saturates instead of wrapping. Changing the native
launch value requires rebuilding and restarting the nodes. Review election
timing together with heartbeat frequency, persistence/transport latency, quorum
read freshness and management request budgets; a larger timeout does not extend
an accepted request's original deadline. See
\repofile|docs/reference/raft-conformance.md|.

The frame router's shared refresh interval is 1000 milliseconds, selected by
\texttt{SNAPSHOT\_REFRESH\_MS} in
\repofile|crates/catten-services/src/lib.rs|. Route refresh, ingress projection
queries and source freshness share that interval; the local VIP admission lease
is five intervals. Backend eligibility uses replication contact no older than
the source-freshness interval, with an acknowledged current-term log entry.
Only a committed availability projection changes the new-flow backend set.
These settings require a service rebuild/restart. Review election timing,
replication latency, projection convergence and flow-history retention together;
a readiness signal or availability change cannot authorize request replay.

\section{Management TLS configuration}

The server collects policy in
\repofile|crates/charlotte-launch/src/management/limits.rs|. Defaults allow 8 client
CA roots, 64 enrolled leaf/role entries, 4 certificates per chain and 8192 bytes
per certificate or server key. Each session permits 65536 input bytes,
65536 output bytes and 16384 application bytes. The send-fragment setting is
4096 bytes; the original handshake and session budgets are respectively
5000 and 60000 milliseconds. One engine step performs at most 32 local TLS
transitions. These are fields of the complete boot profile, not scattered
constants or live overrides. Construction validates and captures them; existing
sessions cannot resize in place.

Generate a complete editable limits file with
\texttt{cluster-sign management-limits-default}. The profile-creation command
requires every named limit, server key/chain, client roots and explicit reader
or administrator enrollments. Unknown, duplicate, missing and inconsistent
settings reject. Seal the private profile with the selected policy's operations
signing key and recipient public key; set
\path{CATTEN_MANAGEMENT_TLS_RESOURCE} to its absolute file path when
building the kernel. Only ciphertext is embedded. The resource is verified and
decrypted at boot using the same prepared kernel trust owner; no service can
select an independent authority. The current delivery mechanism requires a
kernel rebuild and restart to replace the resource.

The exact formats are \texttt{CMGMTL01} inside \texttt{CMGTENC1}. Their central
profile ceiling is 65536 bytes. Both native management services reserve 32 stack
pages (131072 bytes), committed on demand. The management module's
\path{USER_STACK_PAGES} selects this build-time reservation. Review both
dimensions with credentials, buffers, concurrency and service admission.

Smaller fragments increase wire overhead: Rustls subtracts its five-byte header
allowance, and each AES-GCM application fragment adds 22 wire bytes. Validation
checks that maximum application output still fits the selected storage.
Certificates, root hints and all concurrent session buffers must also fit the
service heap/stack and original operation budgets. External buffers do not bound
every Rustls allocation; its current internal handshake-message ceiling is
65535 bytes. Protocol dimensions and cipher safety ceilings are separate from
workload policy. Exact fields, structural bounds and integration gates are in
\repofile|docs/reference/management-tls.md|.

Status uses TLS on port 443; deployment ingress uses TLS on port 7444. Both
require an enrolled client certificate. Readers can observe; mutations require
an administrator before controller dispatch and still require their signed
bodies. Verified host tools require explicit CA, certificate and private-key
files, with an optional server-name override for certificate matching. There is
no plaintext listener fallback.

Rotation or revocation replaces the complete resource, advances the installed
policy revision and restarts both services; existing sessions are not hot
reconfigured. Public development authorities do not establish protected custody
or rollback resistance. Each client obtains a fresh positive time-service
reading before its handshake, under the original deadline; this does not
authenticate the underlying SNTP source. Full execution qualifications and
remaining gates are recorded in \repofile|docs/reference/management-tls.md|.

Established sessions recheck nonzero UTC, the original monotonic budgets and
the enrolled client chain before admitting further work. Chain verification is
cached within one observed UTC second. Expiry, unavailable time or observed
rollback terminates that connection's authority; restoring time does not revive
it. Idle connections continue to wait on resource readiness rather than periodic
expiry polling. This does not authenticate time or prove cancellation of an
already accepted mutation: retain its pending owner and never replay an uncertain
request. Decision logs include the checked UTC second as diagnostic evidence.

The x86 QEMU \texttt{boot\_trust\_test} fixture can compile a different exact
installed signed-policy snapshot using the absolute file input
\path{CATTEN_BOOT_TEST_INSTALLED_POLICY}. Its default is the public revision 7
fixture. The host commits the selected public snapshot before building the
authenticated kernel; the separate boot module must match it exactly. This
input rejects outside that development fixture. It supports restart and
credential-rotation testing, but provides neither protected state nor platform
rollback resistance: an older still-authorized kernel can carry its older
snapshot. Production remains disabled.

\section{Planning and validating a policy change}

Use the following process before selecting a profile for a new workload:
\begin{enumerate}
    \item State the workload: RAM, domains/principals, threads, service topology,
        maximum object sizes, outstanding RPCs and expected overlap during restart.
    \item Inventory each consumed family, unit, sponsor, lifetime and rejection
        result. Include unused candidates, detached work, weak references and
        retained uncertain cleanup. Separate structural bounds from capacity policy.
    \item Measure peak occupancy and rejection under the intended concurrency.
        Choose ordinary capacity and trusted headroom together, explaining
        dependencies and expected failure behavior. A previously passing default
        is not a capacity estimate for a larger workload.
    \item Run the policy harness and strict kernel builds. The harness compiles
        the actual policy, exercises admission counters and rejects inconsistent
        profiles. Compile-time validation checks relationships and arithmetic;
        it does not establish boot viability or essential-service progress.
    \item Boot the exact selected profile on the supported backends. Exercise
        success, exhaustion, allocation rejection, cancellation, restart/generation
        reuse, retained charges and confirmed cleanup. Measure management,
        timer/scheduler and teardown progress against deadlines fixed beforehand.
    \item Preserve the profile, artifact hashes, occupancy/latency results and
        failure diagnostics. Keep failed or interrupted attempts separate from
        successful repeats. Requalify after changing the workload or profile.
\end{enumerate}

These are focused capacity and ownership controls; sustained concurrent pressure and
essential-service fairness remain acceptance work under SEC-07/18.

\section{Extending configuration toward boot resources}

Boot-time installation should reuse this typed policy and its validation, but
must also define a complete authenticated input, reject unknown or incomplete
settings, and establish authority before the first relevant allocation.
Kernel-heap sizing and statically initialized counters currently precede a
general resource-policy installation point. A future implementation must order
those initializations, validate discovered-memory and structural constraints,
then publish one immutable policy before schedulers and services consume it.

Do not implement this by resizing live pools independently. Any future update
mechanism would need a separate account-generation and original-charge contract.
Until that work is implemented and tested, changing capacity means building a
new kernel with a reviewed profile and booting it.
