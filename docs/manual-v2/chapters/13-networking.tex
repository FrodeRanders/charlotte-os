\chapter{Networking}
\label{chap:networking}

CharlotteOS treats networking as an extension of its message-passing and
capability model rather than making TCP/IP the native interface for all
communication.

The guiding principle is:

\begin{quote}
\textbf{Remote IPC is local IPC with a different transport.}
\end{quote}

\section{Why not sockets?}

The Berkeley socket API (\texttt{socket()}, \texttt{connect()}, \texttt{send()},
\texttt{recv()}) has served the Internet for decades. But it is not the right
foundation for a capability-based microkernel:

\begin{itemize}
    \item Sockets identify hosts, not services ---
        \texttt{10.2.3.17:443} tells you where to connect, not what you are
        talking to. The mapping from address to service is out-of-band (DNS).

    \item Sockets are byte streams, not messages --- message boundaries
        are lost. Every protocol invents its own framing on top of TCP's
        undifferentiated stream.

    \item Sockets carry ambient authority --- any process can open a
        socket to any address. There is no capability check; authority comes
        from being able to reach the network, not from being granted a
        connection.

    \item Sockets couple applications to transports --- code written
        against TCP cannot transparently use shared memory for local
        communication or RDMA for high-performance communication.
\end{itemize}

CharlotteOS instead uses layers with separate responsibilities.

The stack below is the target architecture. The current repository contains a
userspace virtio-net driver, an Intel 82574L/E1000E driver, a frame
demultiplexer (``frouter''), a
reliable-message service with fragmentation, a distributed name service that
replicates a \texttt{name $\rightarrow$ \{node, generation\}} catalog across cluster members, a
smoltcp TCP/IP service, and a remote-invocation path through the catalog. The
NIC/TCP path is runtime-validated on macOS QEMU TCG with both virtio-net and
E1000E (\texttt{--relmsg-test},
\texttt{--disco-test}, \texttt{--dns-test}, \texttt{--tcpip-test}), and remote
scalar remote-call prototype is implemented (\texttt{dns::OP\_CALL}); the general
remote capability delegation is not.

\subsection{Ethernet --- generic frame transport}

The NIC driver exports raw Ethernet frames. It knows about MAC addresses, MTU,
and frame CRCs. It knows \textbf{nothing} about IP, TCP, RPC, or services. Its
endpoint protocol has two operations:

\begin{itemize}
    \item \texttt{OP\_SEND(frame\_buffer)} --- transmit a frame via a moved
        memory object.
    \item \texttt{OP\_RECV} --- deferred receive: the caller retains a reply
        token; the driver replies with a received frame buffer.
\end{itemize}

Ethernet is a generic frame transport that can carry IP, ARP, LLDP, custom protocols, 
or CharlotteOS native messages. The driver provides the frames and higher layers 
interpret them.

\subsection{Reliable message layer}

This layer provides sequenced, acknowledged, reliable delivery of \textbf{messages}
(not streams) over the raw frame transport. It handles:

\begin{itemize}
    \item Sequencing (each message has a monotonic sequence number).
    \item Acknowledgements (the receiver confirms delivery).
    \item Retransmission (unacknowledged messages are resent).
    \item Fragmentation (messages larger than MTU are split and reassembled).
    \item Batching (multiple messages in one frame, one ACK for multiple messages).
    \item Congestion control (bounded in-flight windows).
\end{itemize}

The abstraction exported is a \textbf{reliable message}, not a byte stream.
This is the building block for RPC, consensus protocols, and distributed objects.

Fragmentation is implemented: a message larger than one frame's payload (1454
bytes in wire protocol v3) is split across frames that share the message's
sequence number. Every data frame carries a 32-bit total message length; each
fragment additionally carries a 32-bit byte offset and a
\texttt{FLAG\_FRAG}/\texttt{FLAG\_MORE} pair. The receiver validates those
bounds, buffers fragments by offset, and reassembles a contiguous message.

The 32-bit fields separate representation from resource policy. The initial
application-level ceiling is 1~MiB, as configured by
\texttt{relmsg::}\allowbreak\texttt{MAX\_MSG}. This limits
allocation and head-of-line blocking without another protocol revision when
experience supports increasing it. Application IPC no longer packs a MAC and
16-bit length into one scalar: transferred memory begins with a typed 16-byte
v3 envelope containing a magic value, a 32-bit payload length, and the peer
MAC. The per-frame payload length remains 16-bit because it describes only one
Ethernet frame.

Wire protocol v3 carries a 64-bit sender-session identifier. Data and
acknowledgement frames assert it with \texttt{FLAG\_SYN}. A receiver accepts
only a strictly newer session when resetting receive ordering, so one
reliable-message service can restart while its peer remains running and old
delayed frames cannot roll state backward. Receive-message count, queued
bytes, fragment count, aggregate reassembly bytes, and retained outbound bytes
are bounded; a full delivery queue withholds sequence advancement and its
acknowledgement, applying retransmission-based backpressure. An incomplete
fragmented message does not emit one useless cumulative acknowledgement per
fragment, and retransmission grace scales with retained fragment count up to a
fixed cap; one-frame RPCs retain the 200~ms retry. The transport still permits
one in-flight message per peer and retains fragments for retry, so bulk streams
should use a streaming or object-store protocol rather than treating the
32-bit representation as a recommended message size.

\subsection{RPC layer}

The RPC layer provides request/reply semantics over the reliable message layer:

\begin{itemize}
    \item Synchronous-looking futures --- \texttt{service.call(opcode, args).await?}
    \item Asynchronous invocation --- the \texttt{Future} is backed by a
        pending RPC call; the shard continues other work while waiting.
    \item Object references --- the target architecture can represent
        delegated remote authority; general remote capability delegation is not
        implemented.
    \item Serialisation --- typed protocol crates handle encoding/decoding
        between Rust types and the wire format.
\end{itemize}

The implemented DNS v3 remote-call path is narrower than this target model. It
currently carries scalar opcode/argument calls. A request is identified by
caller node, caller DNS-session generation, and call ID, and a reply is
accepted only from the expected peer. The implementation bounds outstanding
calls at 64, returns \texttt{ERR\_UNCERTAIN} after five seconds (execution may
already have occurred), and retains 128 completed results to suppress duplicate
execution within that window. The replicated catalog assigns a monotonically
advancing service generation; requests and replies carry it, and the target
rejects stale generations before execution. Remote object-capability
delegation remains future work.

Registration uses two replicated phases. A \texttt{prepare} command allocates
the next generation but remains invisible. After the owner successfully
publishes its node-local endpoint, a generation-fenced \texttt{activate}
command makes the entry visible. Failed local publication therefore leaves an
inactive tombstone rather than a remotely resolvable ghost. Automatic
replicated unregistration when the hosted service dies remains future work,
but explicit unregistration is implemented. Its replicated tombstone must
match the owning node and distributed generation. Subsequent removal from the
node-local name service must also match the local generation captured before
the proposal, so a delayed operation cannot remove a replacement instance.

Lookup and call-routing decisions do not use follower-local catalog state. A
follower sends a correlated query to the known leader, and the leader answers
only when Graft's quorum-contact read barrier succeeds. Query failure returns a
safely retryable \texttt{ERR\_NOT\_LEADER}; a timeout after remote execution may
have begun remains \texttt{ERR\_UNCERTAIN}. Raft time is supplied by a persistent
detached-timer completion, preventing sustained endpoint traffic from freezing
the lease clock. Catalog and status dumps are diagnostic local observations,
not linearizable reads.

\subsection{Distributed objects}

At the top of the stack, applications interact with \textbf{capabilities} ---
the same abstraction they use for local IPC:

\begin{lstlisting}[style=rustCode]
let payroll: Capability<PayrollService> = lookup("Payroll")?;
payroll.call("calculate_salary", employee).await?;
\end{lstlisting}

The intended API hides whether a service uses local endpoint IPC or remote RPC.
The implemented remote path is limited to the scalar DNS v3 call contract
described above.

\section{TCP/IP as a compatibility service}

TCP/IP is supported as a userspace compatibility service. The frouter owns
the NIC's deferred \texttt{OP\_RECV} and routes IPv4 (\texttt{0x0800}) and
ARP (\texttt{0x0806}) frames to the \texttt{tcpip} service's \texttt{OP\_FRAME}
ingress; a smoltcp \texttt{phy::Device} adapter pulls those frames and transmits via
\texttt{OP\_SEND}:

\begin{lstlisting}[style=rustCode]
// smoltcp adapter (receive is fed by the frouter's OP_FRAME ingress):
fn receive(&mut self, now: Instant) -> Option<(IpPacket, ...)> {
    self.rx.pop_front() // frames queued by the tcpip service
}

fn transmit(&mut self, now: Instant) -> Option<...> {
    // Calls OP_SEND with a memory object.
}
\end{lstlisting}

The TCP/IP stack itself uses smoltcp 0.13. It is wrapped in a userspace
service that registers as \texttt{"tcpip"} and serves clients through a
socket-API protocol (\texttt{OP\_SOCKET}, \texttt{OP\_CONNECT},
\texttt{OP\_BIND}/\texttt{OP\_LISTEN}, \texttt{OP\_ACCEPT}, \texttt{OP\_SEND},
\texttt{OP\_RECV}, \texttt{OP\_CLOSE}). Legacy software that requires TCP/IP
connects to this service.

The architecture runners attach a NIC by default. Hardware discovery starts
the driver and frame router, followed by discovery, cluster services, and the
DHCP-configured TCP/IP service. The \texttt{--no-network} runner option is the
explicit isolated-boot configuration. Options ending in \texttt{-test} add
verification workloads and result reporting; they do not enable the runtime
services.

\section{Cluster-wide TCP ingress and direct server return}
\label{sec:distributed-l2-ingress}

Charlotte can expose one launch-authorized IPv4 TCP service as a cluster
\texttt{VIP:port}. Charlotte therefore supports two complementary addressing
modes. A node's DHCP or static address names that particular machine and is
appropriate for intentionally node-specific client/server traffic. The VIP
names a service in the cluster: an external client need not know which node
admits the packet or owns the connection, and those roles can change without
changing the client's service address.

Direct Server Return is often introduced as a load-balancing technique, and
Charlotte does distribute five-tuples across eligible execution nodes. Here it
also provides a cluster facade. The stable external identity belongs to the
cluster service, while individual node addresses and MAC routes remain
internal placement and delivery mechanisms. In that sense the VIP is another
step toward treating the cluster, rather than a selected server, as the
computer.

This is not a TCP proxy. The frame router that receives an
external frame parses its five-tuple and uses deterministic rendezvous hashing
to select an execution node. A local winner follows the ordinary
\texttt{OP\_FRAME} path into smoltcp. For a remote winner, the router changes
the Ethernet delivery into a compact one-hop Charlotte envelope and moves the
same memory object back through \texttt{net::OP\_SEND}. The envelope carries
the original source MAC and EtherType; the selected backend validates the
outer source against its committed member routes and removes the envelope in
place. IP, TCP options, sequence numbers, and payload bytes remain unchanged.
The
backend smoltcp instance owns the only TCP state and sends its VIP response
directly to the client.

Eligibility comes from the committed configuration of the DNS-owned Raft
member, never from discovery alone. DNS materializes an immutable snapshot of
stable node keys and discovery-associated MAC routes, separating admitted
members from the subset eligible for new flows. The router refreshes this snapshot asynchronously; no consensus operation occurs
on the packet path. During joint consensus, only voters common to the old and
new sets accept new flows. This delays a joiner until finalization and removes
a departing node promptly.

An operator-signed, committed node-shutdown intent removes its target from new
flow selection before local teardown, while retaining its admitted route for
observed flows during the grace interval. The load-balancing epoch is a stable
fingerprint of the committed configuration index and replicated drain
generations. Each
router retains four recent sets and a bounded 1,024-entry
\texttt{FlowKey $\rightarrow$ epoch} table. Observed connections retain their
set across additions; when a backend is removed, only bindings selecting that
backend are released for reconnection. Rendezvous selection is independent of
member ordering, so a replacement ingress participant with the same epoch
selects the same live backend without shared connection tracking.

VIP acceptance and advertisement are separate. Every backend installs the VIP
as a \texttt{/32} smoltcp address, but only the current Raft leader, when it is
in the committed eligible set, passes VIP ARP requests. A newly elected leader
emits gratuitous ARP, so ingress ownership can move without altering backend
membership. The first version supports one IPv4/TCP service and at most 64 backends;
IPv6 neighbour discovery, a service-only drain operation, automatic failed-member
removal, multiple service-specific placement sets, and transparent TCP-state migration are future work. The
precise bounds, failure semantics, and status fields are documented in
\repofile|docs/architecture/distributed-l2-ingress.md|.

The current slice supplies one service declaration as trusted launch policy
and initially treats admitted eligible members as its backend set. It does not
yet derive service-specific eligibility from committed application placement
and readiness. Connecting those two control-plane records is the next step
toward making arbitrarily placed services reachable through cluster identities
without exposing their host nodes.

Operational Vote, AppendEntries, and InstallSnapshot RPCs use private
EtherType \texttt{0x88b7}, while admission and DNS application/control traffic
remain on the reliable-message layer. Joining durably fences and resets the
standalone consensus history before accepting the selected anchor's log.
Append retries that overlap a compacted snapshot skip the compacted prefix;
they cannot duplicate it behind the retained suffix. Forwarded data frames use
EtherType \texttt{0x88b8}. This is an isolation marker rather than
cryptographic link authentication, so the first version assumes a trusted or
administratively isolated cluster L2 segment.

The host-visible \repofile|scripts/run-distributed-ingress-test.sh| fixture
forms a stable three-voter cluster, establishes flows across all three
backends, kills the Raft leader and VIP advertiser, observes the replacement's
gratuitous ARP, and completes an HTTP request over a surviving established
flow. It then opens fresh five-tuples and requires another HTTP exchange with a
live backend, covering reconnect after the failed advertiser also took one
backend connection with it. Failed voters are not removed automatically, so
some new hashes may continue to select the failed node until an explicit
committed membership change removes it; the recovery probe therefore tries a
bounded family of new flows.

\section{UTC time as an internal service}

The userspace \texttt{time} service is a client of the TCP/IP socket API. It
waits for local boot readiness and a nonzero DHCP address, then samples an NTPv4
server over connected UDP. It calibrates the monotonic counter, estimates drift
and uncertainty across samples, prevents time from moving backwards within a
service lifetime, and persists calibration in the object store for holdover.

Applications do not speak NTP. They resolve \texttt{"time"} through the local
name service and call its endpoint protocol for a full snapshot, scalar Unix
seconds, or a fixed-width UTC ISO 8601 value. Synchronization state and
uncertainty are explicit so callers can reject unsynchronized or weak holdover
time. This service starts during an ordinary networked boot; no test option is
required. The detailed wire contract and security limitations are recorded in
\repofile|docs/reference/time-service.md|.

\section{Capability-scoped external data services}
\label{sec:external-data-services}

CharlotteOS has narrow S3 and Kafka compatibility services on top of the
userspace TCP/IP stack. They preserve the capability model at the application
boundary even though they communicate with conventional external systems:

\begin{verbatim}
application
    |
    | delegated endpoint capability
    v
S3 or Kafka service
    |
    | owned TCP socket (+ verified TLS when configured)
    v
managed object store or Kafka broker
\end{verbatim}

An application receives neither a generic network capability nor the remote
credentials and protocol state. Instead, each service instance is provisioned
with one bounded profile. The connection to that instance is the authority to
use only the profile's endpoint, namespace, and operation rights. The
application-side helpers build on \texttt{catten\_rt::owned}: moved memory
pages carry payloads, and each remote stream, delivery, consumer, or transaction
has an explicit consuming teardown plus a best-effort \texttt{Drop} fallback.

These services are not launched unconditionally. A trusted provisioning path
must supply their profiles, including secrets and trust anchors. The
\texttt{--s3-test} and \texttt{--kafka-test} runner options create disposable
Docker fixtures, generate short-lived test certificates, launch test profiles,
and add guest verifiers. They validate integration; production provisioning
does not conceptually depend on those switches.

\subsection{S3 client service}
\label{sec:s3-service}

One \texttt{s3} service instance is fixed at launch to an IPv4 endpoint and
DNS name, port, region, bucket, key prefix, credential identity, optional Dell
EMC ECS namespace, and a GET/PUT/DELETE rights mask. Applications use keys
relative to the granted prefix. The service rejects absolute paths and
\texttt{.}/\texttt{..} path segments, constructs path-style S3 requests, and
signs them with AWS Signature Version~4. The secret key remains inside the
service address space.

The implemented data plane provides streaming GET and PUT, HEAD, DELETE,
ranged GET, and create-only PUT. Object bodies cross the application boundary
as moved, bounded memory chunks; response metadata includes length, ETag,
version id, and request id. The HTTP/1.1 adapter accepts fixed-length and
chunked responses. Bucket listing, multipart upload, presigned URLs, automatic
region discovery, and a general AWS API are not implemented. A LIST right is
reserved in the profile format but currently has no operation.

TLS profiles require an explicit DER trust anchor, a matching server name,
system entropy, and synchronized UTC from the time service. Certificate
verification or entropy failure aborts the connection; there is no downgrade
to plaintext. The S3 request date also comes from synchronized UTC, so a TLS
or signed request fails closed while the clock is unsynchronized.

The AArch64 integration test starts RustFS behind verified TLS and performs a
PUT/HEAD/GET/DELETE round trip. The same client surface is intended for
centrally managed S3-compatible stores. The optional
\texttt{x-emc-namespace} header specifically supports Dell EMC ECS namespace
profiles, but ECS interoperability has not yet been runtime-qualified in this
repository.

The transport-independent Signature V4 and HTTP code lives in
\repodir|crates/charlotte-s3|, the application protocol in
\repodir|crates/charlotte-protocol-s3|, the owned client in
\repofile|crates/catten-services/src/s3_client.rs|, and the service adapter in
\repofile|crates/catten-services/src/bin/s3.rs|.

\subsection{Kafka client service}
\label{sec:kafka-service}

One \texttt{kafka} service instance has a stable profile-selected identity and
grants access to at most 32 explicitly provisioned broker endpoints, a
fixed consume topic/partition, an ordered allow-list of produce routes, a
consumer group, transactional id, and connector rights ceiling. It owns the broker socket,
producer ids, producer epochs, per-route sequence numbers, and consumer-group membership.
Applications can produce idempotently, open a fixed-partition group consumer at
the group's committed offset (or the earliest retained offset), poll with
\texttt{read\_committed} isolation, commit or release a delivery, and close the
consumer.

The complete version-6 broker profile is serialized into one immutable object,
covered by a SHA-256 integrity digest, and transferred to \texttt{kafka} with a
kernel-enforced \texttt{MAP\_READ}-only launch capability. Typed capability
metadata carries the exact meaningful byte length rather than overloading a
generic flags field. The service validates the size, version, digest, UTF-8 DNS
host-label syntax, field bounds, route and broker counts, configurable ceilings,
and duplicate routes or endpoints before opening a broker connection. The hard ceiling is 64
produce routes, while deployment policy may select a lower limit. Metadata for
all distinct declared topics is requested in one broker exchange.
The digest detects corruption; authenticity and provenance come from the
trusted launcher and the read-only capability.

The kernel prepares a profile-backed launch transactionally. An owning launch
object retains the not-yet-running domain, delegated connection, and transient
kernel profile object until read-only transfer succeeds. Allocation,
delegation, or transfer failure closes the earlier resources and the target
address space before an error is returned; a best-effort destructor protects
future early-return paths.

Connector-only authentication uses a bounded sequence of length-delimited
profile sections. Version 6 defines critical SCRAM-SHA-256 and P-256 mTLS
sections, rejects duplicate known sections, and caps both section count and
aggregate bytes. A decoder may skip an unknown optional section but rejects an
unknown critical section, so a future mechanism can explicitly require a newer
connector without exposing its material through the application ABI.

The same digest covers a non-empty printable-ASCII instance name and a bounded
set of separately published authority endpoints, whose names are each at most
256 bytes. Every endpoint carries a Kafka-rights ceiling that must be a subset
of the connector ceiling. The service maps every received opcode to its
required produce, consume, and transaction rights and rejects a missing right
before decoding request memory or creating resources. A producer-only
capability therefore cannot open a consumer or transaction even when the same
connector also publishes a transactional endpoint. Short names use the scalar
name-service path and longer names use its copied-memory path. Applications
cannot create or rename access points through the Kafka ABI.

Only the broker-facing service receives this profile. Producer, consumer, and
transactional-step logic receives a connection capability to one provisioned
authority endpoint, never its broker address, trust material, SASL/SCRAM
credentials, or mTLS identity. Credential rotation can therefore replace the connector
profile without rebuilding application or procedure artifacts.

The transaction owner supports the consume--transform--produce path. An
application can produce records, move one consumed delivery's next group
offset into the same Kafka transaction, and then commit or abort. Committing
consumes the transaction resource; dropping an unfinished transaction attempts
an abort. Dropping an uncommitted delivery releases it for redelivery rather
than silently advancing the group offset. These linear owners make the local
lifecycle explicit, but they do not turn arbitrary application side effects
outside Kafka into an exactly-once transaction.

The connector joins its configured group with the bounded
\texttt{charlotte-fixed-v1} assignor. Each member advertises exactly the
topic/partition authorized by its immutable profile. The group leader assigns
each such partition once; duplicate connectors remain heartbeating standbys
with an empty assignment and can take ownership after membership changes. One
connector admits one local consumer because it owns one membership. Ordinary
offset commits carry the active generation and member id. Transactional offset
commits use Kafka's flexible version-3 schema and carry the same fencing
identity. A rebalance revokes outstanding deliveries, aborts a touched
transaction, synchronizes the new assignment, and reloads its committed offset
before polling resumes. The service loop uses monotonic deadlines to heartbeat
even without application calls. Conventional consumers that do not advertise
this assignor cannot share the group.

The connector's bounded status page reports metadata refresh count and age,
reconnects, retries, terminal failures, fences, group state, consumer lag, and
cumulative records per route. Monitoring derives throughput by sampling these
counters; ordinary application capabilities do not expose the operational view.

For procedures that only implement business behaviour, the generic
\texttt{kafka\_step} service owns that lifecycle instead. Its separate,
read-only profile names one connector and one procedure endpoint, admits only
specific output-route indices, identifies the DLQ route, and bounds output
count, attempts, timeout, backoff, and polling. The procedure receives borrowed
input bytes and an attempt number but no Kafka capability. The runner validates
the complete output batch before beginning a transaction, produces admitted
records, includes the input offset, and commits. Retry replies and procedure
timeouts release the delivery for redelivery; terminal or malformed replies
and retry exhaustion transactionally copy the original record to the DLQ.
Transport and commit failures abort and redeliver without consuming the
business-attempt budget. One owning operation aggregates the call, input
memory, delivery token, and transaction, so cancellation and early-return
cleanup follow the owned-resource rules rather than a manual cleanup ladder.

The wire crate negotiates \texttt{ApiVersions} and implements a deliberately
small set of stable Kafka request versions. Metadata selects partition leaders
and group/transaction coordinators only from the profile's hostname/port and
IPv4 allow-list. Authorized endpoints are alternate metadata seeds, and
retriable produce/fetch failures refresh leader metadata before retry.
Group and transactional operations rediscover a moved coordinator within a
bounded retry budget. The service does not implement topic-pattern
subscriptions, cooperative assignor interoperability, client-certificate
chains, record compression, topic administration, or arbitrary partition
assignment. Records and the number of simultaneous consumers, deliveries,
and transactions are bounded.

TLS uses the same explicit trust-anchor, synchronized-time, and entropy path as
S3. Optional SCRAM-SHA-256 authenticates \texttt{kafka} to every selected broker
after TLS establishment. Optional mTLS uses one DER X.509 client certificate
and an ECDSA P-256 private key; both mechanisms may be required together. The
bounded SCRAM exchange validates broker challenges, minimum and maximum
iteration counts, and the server signature. Passwords, client private keys,
and derived keys use zeroizing owners and remain outside the application ABI.
The opt-in AArch64 test uses a three-broker Apache Kafka fixture over TLS, required mTLS, and SCRAM,
places three-replica input and output routes on different leaders, and verifies
idempotent production, read-committed consumption, atomic production plus
generation-fenced group-offset commit, group generation advance and heartbeat,
transaction abort, filtering of the aborted record, and
the generic step runner's success, retry, timeout, and terminal-DLQ paths. It
also checks metadata refreshes, terminal authorization errors, output-route
production, coordinator refreshes, and non-negative consumer lag in the
bounded status page. After
initial route discovery, the host hard-stops the output-route leader, keeps it
down beyond the connector's bounded receive timeout, and restarts it. The
verifier requires a routing retry and a second successful metadata refresh, so the
result demonstrates replacement-leader recovery rather than merely
steady-state multi-broker connectivity. The fixture selects group and
transactional identifiers coordinated away from the killed broker, isolating
partition-leader recovery from the separate coordinator-migration case.
Because broker exchanges are currently synchronous, the connector requests a
45-second group session while heartbeating every two seconds. The membership
lease therefore exceeds bounded dead-peer detection and route refresh, so
recovering a partition leader does not by itself expire and fence the
transaction's group generation.
A companion fault scenario reads the transaction coordinator selected by
Kafka from the connector's startup diagnostics and hard-stops that broker
after connector bootstrap. It requires transaction-coordinator rediscovery
before the same transaction and generic-step sequence may pass.
A fencing scenario launches a second, independently named connector with the
same transactional identifier. Kafka advances the producer epoch; a private
probe then requires the stale connector to return \texttt{ERR\_FENCED}, publish
a non-zero fencing counter, and enter its diagnostic fault state. Neither the
second connector capability nor either connector's credentials are delegated
to the probe.

The bounded Kafka wire implementation is in
\repodir|crates/charlotte-kafka|, the application protocol in
\repodir|crates/charlotte-protocol-kafka|, the linear client owners in
\repofile|crates/catten-services/src/kafka_client.rs|, and the broker adapter in
\repofile|crates/catten-services/src/bin/kafka.rs|.

\section{Transport independence}

The reliable-message interface is designed to be transport-agnostic. Candidate
transports include:

\begin{itemize}
    \item Ethernet --- for inter-machine communication.
    \item Shared memory --- for co-located processes on the same machine,
        where the kernel can set up shared memory regions instead of going through
        the NIC.
    \item Loopback --- for same-machine same-stack communication.
    \item RDMA --- for high-performance cluster interconnects.
    \item PCIe NTB --- for backplane communication in multi-socket
        systems.
\end{itemize}

The intended RPC layer and everything above it should remain unchanged across
transports.
This is the same principle that makes local IPC transparent to the application
when it moves from same-process to same-machine to different-machine.

\section{Zero-copy networking}

The intended network stack avoids copying whenever practical:

\begin{itemize}
    \item Receive path --- the NIC driver receives a buffer from hardware.
        That buffer (a memory object) is passed up the stack by transferring
        ownership --- first to the message layer (for reassembly), then to the
        RPC layer (for deserialization), then to the application. No intermediate
        copies.
    \item Transmit path --- the application creates a buffer. It is passed
        down by moving ownership. The NIC driver DMA's it directly from the
        application's pages.
    \item Buffer recycling --- after the application consumes a received
        buffer, it returns the (now empty) memory object to the driver's RX pool.
        The driver reuses it for DMA and the cycle repeats. IOMMU-backed pinning
        is implemented with AArch64 SMMUv3 and x86-64 VT-d/AMD-Vi.
\end{itemize}

This is the memory-object transfer model (\autoref{chap:memory-objects}) applied
to networking.

\section{Why the networking architecture matters for critical software}

\begin{enumerate}
    \item Remote invocation follows the local call shape --- the target API
        keeps transport choices out of application protocols. This permits:
        \begin{itemize}
            \item Services can be relocated without application changes.
            \item Testing can substitute a local mock for a remote service.
            \item A common interface can reduce environment-specific application
                code, although the network boundary still introduces failures
                absent from local IPC.
        \end{itemize}

    \item Authority is not an address --- an application invokes a service
        capability rather than relying on \texttt{host:port} reachability. Network
        access alone does not mint that capability.

    \item Copy avoidance is a design goal --- page ownership transfer can
        avoid intermediate payload copies. CPU mappings are MMU-enforced; DMA
        isolation is implemented with SMMUv3, VT-d, and AMD-Vi. No performance
        comparison with sockets has yet been established.

    \item Message boundaries are preserved --- the native abstraction is a
        message with identity, ownership, metadata, and boundaries. There is no
        need for an additional stream-framing layer. This can simplify protocol
        implementations, but does not eliminate parsing or framing defects.

    \item TCP/IP is available but not mandatory --- legacy software
        connects to the TCP/IP service. Native software uses the capability-based
        stack. The transition is incremental: a service can expose both a native
        endpoint and a TCP/IP socket through the compatibility service.
\end{enumerate}
