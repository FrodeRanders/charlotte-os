\chapter{Live Service Upgrade}
\label{chap:live-upgrade}

CharlotteOS has a tested prototype for replacing a reference service while
transferring its state. We describe this as \textbf{restart-with-state}:
in-flight requests may fail during handoff. Clients reacquire a connection and
apply their protocol's outcome/replay policy before continuing.

\begin{architecturalcomparison}{CuriOS and state that survives a service}
CuriOS starts from the observation that restarting an isolated server can
still lose every client's session state. It separates and protects
client-related service state, granting a server access when processing that
client's request so state can survive a server restart \cite{prior:curios}.
CharlotteOS shares the containment goal, but its demonstrated upgrade uses a
cooperating old service to serialize state and move it to a fresh generation.

This makes the handoff format and replacement boundary explicit, without
requiring a general OS-managed store of every service's client state. It also
leaves more responsibility with each service: the old instance must produce
valid state, the replacement must understand it, and clients must handle the
availability gap and uncertain outcomes. An upgrade handoff is therefore not
automatic recovery of state destroyed by a crash. The protocol below and the
\repofiletext|docs/guides/reconnecting-clients.md|{reconnecting-client guide}
define the supported behavior, but arbitrary services, device state and external
side effects need their own recovery protocol.
\end{architecturalcomparison}

\section{The four primitives}

The prototype builds on four primitives implemented in the kernel and name
service:

\begin{enumerate}
    \item Memory-object ownership transfer: the kernel's
        \texttt{memory::object::move\_to} moves a page-backed memory object
        from one address space to another. The sender loses access, and the
        receiver gains it. This is the vehicle for service state.

    \item Generation tracking: the userspace name service records an
        publication generation. Rebinding a name does not revoke a still-live
        old endpoint. Once that endpoint closes, its connections reject, and a new
        lookup can return the replacement generation and connection.

    \item EndpointClose and Cancelled: when a service domain exits,
        the kernel closes its endpoint. Queued requests that were never
        delivered complete as \texttt{EndpointClosed}. Delivered calls whose
        server exited before replying complete as \texttt{Cancelled}. Clients
        receive the corresponding failure result.

    \item Bootstrap capability delivery: the supervisor writes
        initial capabilities to the config page before a domain starts. For a
        live upgrade, the bootstrap contract is extended: in addition to the
        name service connection, the new domain receives the old service's
        state as a memory object. The current reference replacement creates and
        registers a fresh endpoint.
\end{enumerate}

\section{The handoff protocol}

\architecturefigure{handoff-protocol}
    {The live-upgrade handoff: the supervisor drains and transfers the old
    service's state, spawns the replacement with the handoff state and a fresh
    generation, after which clients reacquire a connection and decide whether replay is safe.}
    {fig:handoff-protocol}

The reference echo service receives \texttt{OP\_HANDOFF} from the userspace
service manager. Its single serving loop serializes its counter into an unmapped
memory object and returns that object through a consuming moved-memory reply
before exiting. The manager unregisters the old publication before requesting
replacement launch. A general service needs its own admission/drain protocol, because
this counter handoff does not establish that arbitrary in-flight work is drained.

The supervisor then spawns the new service instance with an extended bootstrap
contract containing the name service connection and handoff state. The new
service deserializes the state, creates a fresh endpoint, and re-registers under
the same name. The name service bumps the generation. Teardown of the stopped
old domain invalidates its stale client connections.

\section{Executable source}

Embedded service images are bootstrap and recovery inputs. They are not the
only executable source. The service manager first tries the object store and
reads the well-known executable object for the target service. The returned
multi-page memory-object capability and exact byte length are passed to
the \texttt{SpawnUpgrade} syscall. If storage is absent or the object is not installed,
the manager selects the embedded recovery image.

The kernel snapshots the capability-backed bytes into kernel-owned memory before
parsing them. It then checks the ELF class, architecture, program-header bounds,
segment bounds, page congruence, W\^{}X (``write xor execute'')\footnote{A memory
page may be writable or executable, but never both simultaneously}, integer
overflow, and whether the entry point lies in an executable load segment.
This prevents a mutable userspace image from changing between validation and 
mapping.

Executable artifacts carry an Ed25519 CLS2 note that binds the complete ELF to
its logical service name, artifact class, release metadata, rollback counter,
policy flags, and signing-key identifier. The loader snapshots the bytes and
verifies the note before mapping. The FNV-1a object checksum remains corruption
detection, while the CLS2 signature supplies executable authority. Rollback policy, key rotation, and measured
boot remain future policy work.

\section{Shared Kernel Preparation}

The live syscall uses the supervisor's complete preparation path:

\begin{lstlisting}[style=rustCode]
pub(crate) fn try_spawn_upgrade_from(
    image: &[u8],
    name_service: &NameServiceHandle,
    rights: ConnectionRights,
    old: AddressSpaceHandle,
    source: AddressSpaceHandle,
    grant: UpgradeGrant<'_>,
) -> Result<ServiceDomain, UpgradeSpawnError>;
\end{lstlisting}

\texttt{UpgradeGrant} borrows source IDs from the captured namespace. The
syscall supplies its authorized manager and at most one state object, while the old
endpoint's exact root generation supplies replacement classification before
loading. Naming, source, old-service and replacement roots remain retained.

\texttt{PreparingUpgrade} owns the launch transaction, every prepared transfer
and both byte-admitted transfer/target-ID vectors. Reserve both arrays before
escrow or delegation. Ordinary failure explicitly disposes the prefix after
guards leave, frees arrays, then cancels the unstarted domain once. The first
cleanup error stops, and abandonment retains all fields and original charges.
Commit publishes the move batch before destination IDs enter the bootstrap page
and the initial thread starts. No implicit physical cleanup or reverse-move
reconstruction runs on parent abandonment.

Native controls qualify original classes, prefix/quota rejection, guarded
parent retention, maximum 31-entry array layouts and real single-state persistent
upgrade. They do not establish 31 simultaneous physical transfers or an
end-to-end multi-state endpoint handoff. See
\repofile|docs/reference/service-launch-ownership.md|.

\section{What the service must implement}

The old service must handle \texttt{OP\_HANDOFF}:

\begin{lstlisting}[style=rustCode]
OP_HANDOFF => {
    // Stop accepting new work.
    // Serialize all mutable state into memory objects.
    // Unmap the state before transferring it.
    // Consume reply authority with reply_move(state, result).
    // Leave the owning serving scope, then exit.
}
\end{lstlisting}

The following sketch describes the launch inputs, rather than an ownership-safe
application listing. The current reference implementation is
\repofile|crates/catten-services/src/bin/echo.rs|, and handoff memory is adopted once
at that documented launch boundary, while the bootstrap connection is borrowed.

fn main(ctx: Context) -> ! {

    let state_count = ctx.handoff_count();

    // under the same name (NS bumps generation), start serving.

\section{What clients see}

A closed old endpoint rejects further calls. Queued, undelivered calls return
the endpoint-closed result, but delivered calls that lose their server before a
reply return cancellation. A timeout or cancelled reply does not prove that a
delivered request had no effect. Name rebinding alone supplies no such proof.

The copyable client in \autoref{sec:reconnecting-client} keeps business progress
outside its session connection, maps endpoint closure to an application-defined
restart decision, and preserves one operation deadline across reconnection.
It stops on an uncertain accepted call. Its read-only business operation can be
repeated safely, but a mutating protocol needs durable request identity, duplicate
suppression and outcome reconciliation before replay. Grant-mediated discovery
must also authorize the replacement publication.

\section{Restart-with-state vs.\ zero-downtime}

This design is \textbf{restart-with-state}: in-flight requests to the old
instance can fail during the handoff window, and clients need a recovery policy. It is
potentially suitable for services whose protocols define retry and state
recovery. No general latency bound has been measured, and clients must
explicitly handle temporary failures through name-service re-lookup.

True zero-downtime would require one of:

\begin{itemize}
    \item Queue migration: the old service's endpoint queue would
        need to be transferred to the new service atomically, so no request
        is ever rejected. This is a future kernel feature.
    \item Sidecar model: the new service starts alongside the old
        one, both sharing the same endpoint, and the old service stops
        accepting new work. The kernel does not currently support multiple
        owners for one endpoint.
\end{itemize}

\section{Relationship to crash recovery}

The live upgrade path is the graceful variant of the crash-recovery path
already exercised by the UART driver test (\autoref{chap:userspace-drivers}). In both cases, the
supervisor arranges a replacement and a fresh publication. Driver recovery also
requires confirmed device quiescence/reset before grants can be reused, and
uncertain cleanup may retain backing and prevent restart. The difference is that live
upgrade transfers state explicitly through memory objects before the old
instance exits, rather than starting the new instance from scratch.

\section{Upgrade guarantees and limits}

\begin{enumerate}
    \item The reference path transfers service state: the self-test
        demonstrates handoff for the reference service. Filesystems, network
        stacks, and consensus nodes would each need protocol-specific
        serialization, compatibility, and recovery work.

    \item The upgrade sequence is explicit: the old service drains
        in-flight work, serializes state, and exits. The new service starts
        and registers. Clients reconcile failed work. A hard time bound is not currently
        enforced or benchmarked.

    \item Failure recovery has an ownership model: if the new service
        fails to start, a future supervisor could restart the old service or a
        fallback.
        Before transfer, the manager holds the state capability, and after
        transfer, it belongs to the replacement. Recovering state after that
        replacement fails requires an explicit policy, beyond capability
        cleanup.

    \item The building blocks are covered by self-tests: memory-object
        transfer, generation tracking, deterministic teardown, and bootstrap
        delivery are exercised by the existing self-test suite. This evidence
        does not establish crash consistency, arbitrary-service compatibility,
        or production readiness.
\end{enumerate}
