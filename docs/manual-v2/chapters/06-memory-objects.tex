\chapter{Memory Objects: Ownership That Crosses Boundaries}
\label{chap:memory-objects}

A memory object answers: \textbf{``Where is the data, and who owns it?''} It lets
page-backed data cross protection-domain boundaries with explicit ownership and,
for move and borrow modes, without copying the payload.

\section{The problem with copying}

In a conventional OS, moving data between processes typically means copying:
the kernel reads from the sender's address space and writes to the receiver's.
For large payloads (packet buffers, file blocks, IPC messages), this copy
dominates the cost of the operation.

Unrestricted shared memory avoids the copy but permits two processes to modify the
same pages. Correctness then depends on synchronization rather than page-table
exclusivity.

CharlotteOS adopts a third approach: \textbf{ownership transfer through page-table
manipulation.} When a memory object moves from one domain to another, the kernel
changes the page-table mappings. The sender loses access; the receiver gains it.
No bytes are copied. The MMU enforces the ownership.

\section{First-class memory objects}

A memory object is a dedicated kernel object representing page-backed storage with
explicit ownership and capability semantics. The kernel manages:

\begin{itemize}
    \item Physical frames: the backing storage.
    \item Mappings: which domains have virtual addresses pointing to
        the pages, and with what permissions.
    \item Ownership: which domain currently holds the master
        capability.
    \item Transfer state: whether the object is idle, in transit,
        borrowed, or undergoing DMA.
    \item Lifetime: when the object is freed, all mappings are
        revoked and all capabilities to it are invalidated.
\end{itemize}

Userspace never exchanges raw pointers across protection domains. Instead, IPC
messages attach \textbf{memory-object capabilities} with declared transfer modes.

\section{Aggregate admission and sponsorship}

The kernel reserves backing pages and one object-accounting unit before each
allocation. One generation may sponsor at most 64 MiB and 1,024 backing objects,
with the page ceiling reduced on smaller nodes. The node's memory-object pool
is at most one quarter of usable RAM and 8,192 objects. Ordinary domains may
consume three quarters of that pool; the remainder is available to
supervisor-designated platform domains. Allocation must also leave one eighth
of usable physical frames free. Platform domains still obey per-domain and
node-wide limits.

One verified artifact principal also shares a ceiling of 16,384 pages across
memory-object, committed heap, ELF/runtime, private-table backing and maximum
user-thread stack capacity, plus 1,024 memory-object
allocations. Every instance and generation consumes that same counter in the
existing principal-history record. The signed loader prepares its immutable sponsor before architecture root
construction and validates that binding before optional preparation and thread
publication. A new instance, ASID reuse or platform
promotion cannot reset it. Existing generation and node pools still apply.
See \path{docs/reference/principal-backing-admission.md}.

\textbf{Sponsorship is distinct from ownership.} A move transfers the authority
to use or destroy an object, while its charge stays with the creating
generation until the physical frames and object record are released. A copy reserves new backing
storage against the copying caller, even when another domain receives it.
Borrowing and pinning retain the existing charge. This prevents a sender from
shedding its budget merely by filling a privileged receiver's queue.

Charges survive sponsor retirement, mapping shootdown and delayed DMA or copy
completion. A reused ASID receives a separate generation budget; late releases apply only
to the retired generation and original principal. Staged-allocation owners roll back failed admission
and allocation. A failed physical release quarantines its charge rather than
creating fresh headroom.

Global object-record storage is prepared fallibly with private backing after
page/object admission. Direct allocation and copies claim a nonreused kernel
object identity before authority publication; publication only relinks prepared
storage. Cancellation leaves identity gaps. Read-loan, memory-capability and
namespace records now also prepare before mutation and relink at publication.
Mapping records and frame-snapshot capacity now also prepare fallibly outside
the memory registry. Scratch namespace and extent nodes now also prepare outside
their local registry, with exact-generation/current-space revalidation.

Mapping preparation now owns its partial node and shared snapshot in inert
fields before either factory. Ordinary constructor rejection and every
constructed completion/rejection explicitly dispose after local memory/table
guards. Abandonment retains partial, complete unpublished and published-snapshot
storage without allocator entry. Final admission checks the captured full
namespace generation before mapping/pin publication. Existing root and physical
completion policies remain required; no retry owner or cleanup authority is added.

Copy-pin frame snapshots likewise prepare fallibly outside memory serialization,
before any frame identity or source pin is retained. Final namespace-generation,
object/size and rights/loan/DMA/mapping checks precede snapshot fill and pin
publication under one hold. Ordinary rejection disposes unused capacity after
unlock. Bare preparation/pin abandonment retains snapshot metadata without
allocator entry; explicit unpin frees it before decrementing the backing fence.
Empty source-escrow retention pins use this same owner without a snapshot.
Aggregate principal admission, automatic scoped/source-transfer destructors and
wider IRQ/guard contexts remain separate qualification.

Mapping/copy/DMA frame snapshots now share requested buffer-byte/count admission:
4 MiB/8,192 total and 3 MiB/6,144 ordinary. The exact calling namespace's trusted
classification is captured before allocation. One inert buffer owner carries its
original charge through preparation, publication, root retirement and abandonment;
actual buffer free precedes refund. Late promotion and ASID reuse cannot reclassify
that reservation. Empty source-escrow pins have no buffer allocation or quota.
Allocator overhead, inline metadata, aggregate principals and sustained concurrent
progress remain separate; see \repofile|docs/reference/snapshot-buffer-admission.md|.

DMA snapshots now use the same inert vector preparation outside memory
serialization. Full namespace/source and direction/rights/loan/exclusion checks
revalidate before allocation-free snapshot fill and shared/exclusive counter
publication. The infallible clone after counter mutation is removed. Bare DMA
pin fallback retains snapshot and original backing fences; explicit snapshot
free precedes unpin. Existing backend operation/maintenance owners still supply
the hardware completion proof. No readiness, recovery family or replay authority
is added. Concurrent snapshot budgets and broader outer contexts remain open.

Retirement keeps the complete detached object node in the existing backing
receipt, with its original frame vector, charge and metadata. Physical release
uses sixteen-frame batches; a started/failed fence precedes allocator entry.
Only confirmed physical completion and actual payload/node disposal permit
charge refund. Inert backing fields retain all state after interruption or
failure, without physical retry. Ordinary rollback and wider caller contexts
retain their separate qualification. See
\repofile|docs/reference/memory-object-storage.md|.

\paragraph{Capability and namespace storage.}
Direct allocation, copies, moves and loans now prepare both payload and namespace
nodes fallibly after exact shared authority reservation. Factories leave memory
serialization; captured namespace generation is checked before publication.
Commit only relinks prepared nodes. Unused namespace candidates remain with the
containing preparation for post-guard disposal. Ordinary loan cancellation drops
unused borrower storage before its destination reservation refunds.

Retired capability nodes retain their exact authority. Explicit disposal frees
payload metadata before authority metadata and original admission. Moves carry
the detached source payload with the same source escrow; loan cleanup pairs the
full payload/authority node with its borrower. Direct close and final-pin cleanup
retain these nodes in the complete object/backing receipt through physical proof.
Failed release retains original backing and authority charges. Namespace cleanup
detaches and drains its complete node after memory unlock, without a snapshot or
new recovery ticket. Source-escrow and wider factory/destructor/IRQ contexts,
general metadata-byte admission and sustained pressure remain open.

\paragraph{Mapping storage and maintenance.}
After preflight, one preparation allocates an empty mapping node and frame-snapshot
capacity outside memory serialization. No frame identity or pin crosses that
factory interval. Captured object/size and every admission predicate revalidate
before snapshot fill, node relink and existing pin acquisition. Page-table walking
and prefix rollback keep their previous serialization; unused snapshot disposal
leaves both local guards.

Rejected-prefix rollback carries its original detached node and exact published
prefix in the same pin until invalidation and required scratch completion.
Explicit unmap keeps its live record through those proofs, then frees the detached
node before pin decrement/backing release. Revocation uses that pin too. Namespace
retirement retains complete admitted mapping nodes and exact peer leases on
failure/abandonment; physical success permits node disposal, then peer completion.
No new physical proof, recovery registry or retry authority is added. General
metadata-byte admission, concurrent unused preparations and broader enclosing
contexts remain separate qualification work.

These are initial kernel admission policies, independent of telemetry filtering
and placement feedback. Signed deployment fields and a userspace policy API for
these limits remain future work. Demand-backed heaps and ELF/runtime pages have
independent generation-owned accounts and node pools, alongside the shared
principal ceiling. Capability records,
IPC operations and several completion/observer families also have separate
admission. Private translation tables also consume that same principal allowance, including
initial roots and cached sparse branches. They retain owning-root limits and a node pool;
fresh shared runtime kernel tables have a separate node pool. Inherited boot
tables/stacks, IOMMU tables, general kernel heap and comprehensive metadata
accounting remain open.

\subsection{Stack capacity admission.}
Before backing allocation, each runtime user-thread slot reserves its configured
maximum user pages plus sixteen kernel pages in a separate node stack pool.
The pool uses one eighth of usable RAM; ordinary domains may consume three
quarters, leaving trusted-platform headroom. A root has at most 64 exclusive
slots and at most 64 user pages per slot. User backing still grows on demand.
The complete maximum user-plus-kernel data footprint consumes the shared signed
principal allowance before frame allocation. A typed share remains with the
original slot/root owner through uncertain cleanup; only unused cancellation or
confirmed pair release refunds it. Data growth pays once, while new private
table branches still have their own charge.
One owning transaction retains both stack ranges, the original root lease and
the reservation through physical cleanup. Refund requires confirmed release of
both ranges; failed or abandoned cleanup retains the entire maximum charge and
slot even if other pages were freed. Kernel-only threads reserve sixteen pages
from trusted admission. Inherited boot/CPU stacks remain outside this runtime pool.

\subsection{Translation-table lifetime.}
Removing a page mapping clears the leaf while retaining empty intermediate
tables in their owning hierarchy. Subsequent mappings reuse those tables;
quiescent address-space teardown releases the complete private tree. Hardware
page walks do not take software locks, so an empty table cannot be recycled
merely because its last leaf was removed. New table backing is initialized
before its parent link becomes valid.

Retained tables follow the hierarchy's high-water footprint and consume their
own admission limits. Shared physical data still requires independent
user translation trees in each domain. Kernel trees are shared and must be
accounted for once. Automatic promotion of an empty subtree to a large-page
leaf is not implemented. Returning an unmapped data frame likewise does not
authorize reuse before translation invalidation has completed. Kernel-range
cleanup now retains removed data in an owning retirement receipt, releases its
arena/page-table guards, then invalidates before recycling. Failed preparation
retains its installed prefix through the same boundary. Forgotten or incomplete
cleanup quarantines backing. On x86, checked invalidation uses bounded,
epoch-qualified acknowledgement and rejects masked post-bootstrap initiators.
Failed delivery cannot count as acknowledgement. Retained owners permit
invalidation retry only before physical release starts; broader caller-context
qualification and recovery of abandoned owners remain hardening work.

Memory-object mappings carry a separate retirement pin through invalidation.
A returned map rejection before acquiring that pin made no mapping publication
or table change in that call. It returns unused scratch without TLB maintenance.
Admitted calls still invalidate after rejected/rolled-back prefixes; the error
alone cannot permit early pin release. Kernel errors retain the per-call
invalidation cause. x86 timeouts include their owned epoch and a sampled first
missing target, which supplies no release or retry authority. The syscall still
reports uncertain status 9. See
\repofile|docs/reference/memory-object-retirement.md|.
The final DMA or copy unpin cannot release backing during that interval, and
borrower cleanup retains loan restrictions until the fence completes. Failed
detach or abandoned cleanup retains both backing and its original sponsorship
charge. Partial installation records only the published prefix; cleanup checks
leaf identity and leaves a foreign collision mapping untouched. Domain cleanup
moves existing mapping records one object at a time, without temporary teardown
vectors. It prepares the records under the object registry, then releases that
guard before detaching leaves. The retained pin supplies borrowed frame identities
in fixed stack batches, so ordinary unmap, loan revocation and domain cleanup no
longer nest the object registry across address-space table walks. Larger objects
use successive batches without allocating a teardown snapshot. These owners
retain exact-generation root operations through physical completion. Loan
revocation, IPC reply/cancellation and staged namespace close compose those
owners so invalidation leaves their local lifecycle/IPC guards first. An
unrelated outer masking guard can still prevent progress; this local separation
does not qualify every caller or destructor. See
\repofile|docs/reference/live-address-space-operations.md| and
\repofile|docs/reference/hardware-quiescence.md|.

Scratch reservation metadata is prepared fallibly before publishing a virtual
range. Namespace and sorted live-extent records use admitted nodes prepared
outside scratch serialization; gaps are implicit. Release detaches one exact
reservation without allocating a free-list node, then frees it after unlock. Partial, combined or
duplicate releases are rejected. Bulk mapping retirement retains its backing
pin and loan restrictions if any scratch completion fails, even after successful
translation invalidation. Completed ranges may be reused; rejected ranges remain
reserved. This strengthens completion without introducing a live-generation
lease or a comprehensive kernel-metadata budget.
MMIO retains its existing root/descriptor claim while scratch preparation also
leaves the device registry; mapped-state admission rechecks atomically with that
claim. Whole-root sealing carries the complete scratch namespace and extent nodes
in its existing metadata/root receipt through final invalidation. Failure or
abandonment retains them; confirmation permits post-guard node disposal before
root backing/slot completion. No separate recovery ticket or physical/replay proof
is added. Scalar range matching still supplies no allocation nonce, and general
metadata-byte/principal admission and wider caller contexts remain open.

Scratch namespace and extent layouts now share 512 KiB/8,192 nodes in total,
with ordinary preparation limited to 384 KiB/6,144 nodes. Admission precedes each
allocator, capturing the exact root's trusted classification once. Partial and
unused candidates, live reservations and detached metadata retain their original
requested bytes/counts through actual node deallocation. Later promotion and
ASID reuse cannot reclassify the refund. Ordinary rejection disposes explicitly;
abandonment retains node and charge without counter entry. Allocator overhead,
aggregate principal metadata and sustained concurrent progress remain separate.

Final user-root destruction now follows a separate two-phase boundary. Logical
cleanup detaches the private hierarchy into an owner that leases its software
slot. After lifecycle and table guards are released, that owner invalidates
translations, destroys backing and completes the slot lease. ARM uses the owned
hardware tag rather than looking up the detached software entry. A replacement
cannot reuse the slot or tag before completion; failed or abandoned cleanup
retains the hierarchy and its charges. This corrects the final root boundary,
while earlier mapping, loan and device invalidations still need lock-safe
retirement phases. Domain supervision must establish thread quiescence first.

A separate live-operation lease retains an exact software generation before
detachment. Its linear table/slot/generation token survives moving metadata.
Root close rejects outstanding leases before subsystem retirement; only explicit
completion of the last lease permits normal close. Abandonment retains the live
root, tag and charges. Public memory-object and MMIO map, map-any and unmap calls retain an operation
lease through page-table changes and TLB invalidation. MMIO also holds a
capability claim so close cannot consume it midway through mapping. Explicit
device close detaches its authority under lifecycle/device serialization and
retains a root lease while invalidating after releasing those guards. Direct
loan revocation retains leases for both owner and borrower. Its transaction owns
the existing borrower state and a backing pin until leaf removal, invalidation,
scratch completion and borrower-capability removal succeed. A failed or
abandoned transaction retains its backing charge and revocation fence.
Successful revocation preserves the object's other read borrowers.
Read-borrower records use admitted nodes retained in the existing prior-state
owner. Failed completion or abandonment keeps the complete map with its fence
and backing pin. Confirmed removal carries the detached borrower node and exact
shared authority past the memory guard; node disposal precedes authority metadata
and original charge release. Namespace cleanup uses that same pairing. Final
object release drains remaining borrower nodes only after physical completion.
Memory capability/namespace and mapping maps, wider containing contexts and
aggregate metadata budgets remain separate qualification work.

An owned staged-close request fences new operation
leases while older leases drain. Pending poll returns
the request owner without subsystem retirement; once ready, cleanup proceeds
through the detached-root boundary. Dropping the request or exhausting its
lease-drain waiting budget retains the closing root, tag, slot and charges.
Later completion cannot reopen admission. The fence applies to operation leases,
not all existing resource paths, and the waiting budget does not bound hardware
rendezvous. All existing borrowed-memory reply variants retain both namespace
leases and a reply claim across IPC-unlocked invalidation. Returned authority
remains hidden until publication. Explicit call/reply cancellation also owns both
roots through unlocked loan cleanup. Bulk endpoint/domain IPC cleanup borrows
its existing close owner and retains one complete cancellation at a time across
unlocked loan revocation. Whole-domain device cleanup prepares its typed receipt
under lifecycle, then releases local guards for device invalidation and cleanup.
Deployment and node-shutdown
supervisors retain a teardown owner across polls and refuse
to report reclamation after a terminal error. They do not reclaim a root whose
close failed or whose leases did not drain.

Namespace cancellation now rechecks the exact token after rejected preparation.
A peer close may have consumed the selected token while IPC serialization was
released. Confirmed absence permits rescan through the same closing owner;
every still-present token or claim remains Pending. This check supplies no
physical or whole-namespace completion proof, adds no busy-token retry and
restarts no deadline. A deterministic control reproduces the earlier stale
Pending result; its connection to the historical live timeout remains unproven.
See \repofile|docs/reports/audits/2026-10-22-ipc-namespace-selection.md|.

Each closing owner keeps its last actual Pending observation inline: the
checked preflight's root-lease count and stage, the selected IPC token/call and
claim epoch, or the memory object's transfer/revocation flags and pin counts.
The supervisor logs its captured root ID/generation, error and last observation
on terminal failure, after local guards leave and before abandoning the owner.
IPC selection precedes cancellation preparation and can become stale across an
episode change. These diagnostics grant no cleanup or retry authority, and do
not change the five-second policy. The earlier cancellation-stress reclamation
timeout remains unresolved. See
\repofile|docs/reports/audits/2026-10-22-root-retirement-diagnostics.md|.

Physical teardown makes heap, image and private-table charges nonrefundable before releasing
any owned frame. Both architecture destructors attempt the bounded private-tree
and data-frame cleanup; only complete success permits account refund. If one
release fails, the whole charge remains consumed, even if other frames were
returned. There is no automatic retry of a partially destroyed hierarchy.
After proven translation quiescence, the software slot and hardware tag can be
reused independently of these retained charges. Failed invalidation instead
retains the complete root, tag and slot. Successful private-tree teardown excludes
previously quarantined provisional table charges from its refund. Shared kernel
charges are independent of that private teardown and remain consumed.

Heap and image preparation jointly own the provisional frame, its reservation
and an exclusive borrow of the original address space. The caller retains the
table guard through initialization, mapping and ownership transfer. Rollback
refunds only after confirmed physical release. A rejected release continues to
consume the original domain ceiling and node pool; successful root destruction
excludes those quarantined pages from its refund. Slot reuse and platform
promotion cannot recover or reclassify the retained charge. If publication is
unconfirmed, cleanup retains backing without attempting deallocation. These
are fixed account counters; recording a failure does not grow a recovery queue.

Translation roots and intermediate tables also have an owning preparation
through publication. Private lower-half tables preserve the physical progress
floor on each allocation; shared higher-half kernel tables may consume that
reserve. Mapping failure can leave a partial linked tree, which remains owned
for retry or quiescent destruction. ARM allocates the root before acquiring a
hardware tag, releasing the unpublished frame if tag admission fails. This
preparation reserves private frames against the original root account and fresh
shared kernel frames against a separate node pool before physical allocation.
Private roots admit at most 1,024 table frames; their node pool uses one sixteenth
of usable RAM with one quarter reserved from ordinary domains. Shared runtime
tables use one sixty-fourth of usable RAM and retain their charges for the kernel
lifetime. Copying shared links does not charge again, and user-root destruction
cannot refund them. Rejected release and unconfirmed publication retain backing
and admission. Inherited boot tables remain outside runtime admission. This
does not resolve remaining lock-held invalidations or general metadata admission.

\section{Four transfer modes}

CharlotteOS defines four transfer modes. Transfer publishes capability authority;
the receiver maps the delivered object separately. Queued attachments and
unobserved returned objects stay inaccessible until receive/result observation.
Moves and write loans require unmapped source backing. Read loans permit existing
read-only mappings, but reject writable mappings. The owning runtime separates
\texttt{OwnedMemory} from \texttt{MappedMemory} so normal callers unmap before
moving or lending rather than relying on an implicit mapping change.

\subsection{Copy}

The receiver gets a byte-for-byte duplicate. The sender retains the original,
unmodified.

\begin{itemize}
    \item \textbf{Use when:} the data is small, the sender needs to keep using it,
        or the receiver is not trusted with the original.
    \item \textbf{Kernel work:} allocate charged private frames, copy a protected
        source snapshot and publish a destination memory capability. The
        receiver maps its copy when needed.
    \item \textbf{Semantics:} simplest; both domains can read their respective
        copies independently.
\end{itemize}

The kernel performs the potentially large byte copy without holding the
interrupt-masking memory-object or frame-allocator locks. Before releasing the
registry lock it acquires a shared-read copy pin on the source object. That pin
keeps the frames alive and rejects every tracked operation that could introduce
a writer until the snapshot is complete. Rejected operations include a writable
CPU mapping, an in-kernel write, a writable or exclusive DMA pin, a write lend,
a move, and ownership rollback.
Read-only mappings and DMA pins may coexist. If the source domain exits during
the copy, destruction is deferred until both the copy-pin and DMA-pin counts
reach zero; physical frames are freed only after the registry lock is released.

\subsection{Move}

Ownership transfers to the receiver. The source must already be unmapped; the
sender's capability is consumed. The receiver becomes the new owner, responsible for subsequent
transfer or destruction.

\begin{itemize}
    \item \textbf{Use when:} the sender is finished with the data and wants to
        hand it off without copying.
    \item \textbf{Kernel work:} validate ownership and unmapped/unpinned state,
        reserve destination authority, escrow the source and commit the
        capability transfer with IPC publication.
    \item \textbf{Semantics:} physical pages stay in place. The sender's old
        capability cannot map them again; the receiver owns subsequent access.
\end{itemize}

\subsection{BorrowRead}

The receiver gets temporary read-only mapping authority. The sender retains
ownership. Confirmed reply/cancellation cleanup revokes the loan, including
any receiver mapping; failed cleanup retains its fence and backing.

\begin{itemize}
    \item \textbf{Use when:} the receiver needs to inspect data but must not
        modify it.
    \item \textbf{Kernel work:} reserve exact destination authority and prepare
        a fallible borrower node before source escrow, outside the memory
        registry. Commit relinks the node and publishes the read-only capability.
        A later receiver mapping must be read-only.
    \item \textbf{Semantics:} writable aliases in the receiver are forbidden by
        the page-table permissions. The receiver cannot write even through unsafe
        code. Revocation at reply time unmaps the pages.
\end{itemize}

\subsection{BorrowWrite}

The receiver gets exclusive writable mapping authority while the sender retains
ownership. The source must be unmapped before admission; the active loan rejects
new lender access. Confirmed revocation ends that restriction. A reply or timeout
without successful cleanup cannot restore access.

\begin{itemize}
    \item \textbf{Use when:} the receiver needs to write into a buffer the sender
        will later read (e.g., a read-into-user-buffer pattern). This is
        \emph{mutable lending}.
    \item \textbf{Kernel work:} validate unmapped, exclusive source state,
        publish borrower authority and retain the revocation contract. The
        receiver may map writable until confirmed cleanup revokes it.
    \item \textbf{Semantics:} the hardware enforces mutual exclusion. The sender
        cannot map the pages while they are lent out. Access through a revoked
        mapping faults even from unsafe Rust; a stale pointer grants no authority.
\end{itemize}

Borrowed-memory replies, including returned connections or memory, retain both
namespace generations, the loan revocation receipts
and an exclusive reply claim in one kernel operation owner. Loan detachment,
TLB invalidation and scratch release then run without the global IPC lock.
A concurrent close of the pending-call or reply capability waits outside that
lock until cleanup finishes; it cannot release the caller's borrow early.
Successful loans are recorded individually, so a later failure keeps only the
remaining loans for cancellation. Only unstarted preparation may restore loan
state: uncertain cleanup retains its backing pin and revocation fence. An
abandoned reply retains its claim and both roots, with no forced reclamation.
Returned connections keep their destination authority hidden until publication
and retain the minting source through the reply claim. Source-close waits
outside IPC as well. Queued connections and unobserved returned connections
cannot serve as retained minting sources: an earlier operation can still reclaim
them. Delivery or observation must precede the reply. An unrelated endpoint-owner
domain may close, making the service unavailable, while the delegated source
keeps the closed endpoint record alive. Failure refunds unpublished grants;
abandonment retains the source claim and both roots.

Returned memory retains its source escrow, backing pin and hidden destination
reservation in the same operation owner. The output must be owned and unmapped;
queued or unobserved-result memory must first be delivered or observed. Memory
close waits outside the registry for the transfer owner. Rollback restores source
authority and releases its pin under one registry hold, so close never observes
restored authority with an unfinished transfer pin. Serialized cleanup uses a
nonwaiting busy check instead of parking beneath IPC. After input-loan cleanup,
the output move and any returned connection publish jointly before result
visibility. Ordinary failure restores the unstarted output move; abandonment
can also restore that output, but retains uncertain input-loan backing and the
reply/root claims. No-loan replies remain atomic under IPC.

Explicit close of a pending call or delivered reply composes both namespace
leases, every loan receipt and an exclusive completion claim in a cancellation
owner. A queued message stays in place while its loans are detached and
invalidated outside IPC: receive reports Pending, and endpoint close waits
outside the lock. Success records all revocations before consuming authority
or notifying the caller. Failed cleanup leaves the capability live and reports
no terminal result; untouched preparations roll back, while uncertain backing
stays fenced. Abandonment retains the queue, claim and both roots.
Endpoint readiness excludes claimed or failed queue fronts. Removing queued
work re-signals receivers and their bound completion queue after unlocking,
so later work can proceed. A failed request remains fenced from delivery/reply.

The runtime's explicit \texttt{PendingCall::close} returns its owner on error,
preserving the Rust borrow. Drop and consuming waits cannot return an owner;
if close fails, they abort the domain instead of ending a potentially unsafe
borrow. The domain terminates, but that alone does not establish that resources
can be reclaimed.
Bulk endpoint/domain cleanup remains serialized. Its reply-token cleanup must
retain failed loans without reporting them as completed; full bulk ownership
and failure recovery remain work in progress.

\section{Why hardware enforcement matters}

Page tables enforce the transfer modes across protection domains:

\begin{itemize}
    \item A C program running in a protection domain cannot violate the
        constraints any more than a Rust program can.
    \item A buffer overrun cannot read pages that are not mapped.
    \item An unsafe block cannot write to a \texttt{BorrowRead} buffer.
    \item A use-after-drop cannot resurrect a moved memory object.
\end{itemize}

Rust's ownership complements the kernel enforcement by catching errors within a
domain at compile time. The kernel is the ultimate guarantor for cross-domain
safety, so non-Rust or buggy-Rust processes are still contained by page tables and
capability checks.

\section{Control plane versus data plane}

Endpoint IPC belongs to the \textbf{control plane}: it configures connections,
carries opcodes, sets up device queues.

Memory objects belong to the \textbf{data plane}: they carry the actual bytes
(packets, blocks, buffers, strings).

For networking specifically:

\begin{itemize}
    \item Control plane: endpoint IPC configures NIC queues, sets MTU,
        registers buffer pools.
    \item Data plane: descriptor rings coordinate producer/consumer
        state; packet payloads move as memory objects.
\end{itemize}

This separation avoids turning every packet into a copied IPC payload while
preserving strict ownership.

\section{DMA as a third ownership dimension}

When a device performs DMA, a memory object enters a third ownership state:

\begin{itemize}
    \item CPU ownership: the CPU reads and writes the pages normally.
    \item DMA ownership: the device is reading or writing the pages; the
        CPU must not access them.
    \item Rust/API ownership: which domain holds the capability.
\end{itemize}

The AArch64 SMMUv3 and x86-64 VT-d/AMD-Vi paths track an explicit DMA pin per
mapped memory object. The kernel validates access direction, installs only the
object's frames in a device-private translation context, and releases the pin
only after a synchronous IOTLB invalidation. Drivers receive IOVAs rather than
physical addresses. CPU mappings are not automatically revoked at the raw
syscall layer, so coherent descriptor rings remain an explicit driver protocol.
Ordinary Rust applications should instead use \texttt{catten\_rt::owned}:
calling \texttt{unmap} on \texttt{MappedMemory} consumes the CPU mapping, and
only the resulting \texttt{OwnedMemory} can create a \texttt{DmaTransfer}.
The memory cannot be mapped or exposed as a Rust slice again until the
transfer's \texttt{finish} method has synchronously removed the IOMMU mapping.

A failed DMA unmap retains the Rust owner. Only an explicit
\texttt{OPERATION\_IN\_FLIGHT} admission rejection permits another submission;
other failures retain the original status without repeating DMA unmap from
\texttt{finish} or \texttt{Drop}. The attempt is recorded before kernel entry.
For shared coherent memory, confirmed DMA completion is retained across a later
CPU-unmap failure. Best-effort local teardown does not release uncertain kernel
DMA pins or their backing charges.

Both DMA-map syscall forms return status, IOVA and a per-call diagnostic
stage/cause. Backend rejection includes admission and started maintenance;
it does not prove rollback or authorize retry. A shared-DMA setup failure
retains its existing CPU mapping in \texttt{FailedSharedDmaMemory}, which exposes
no slices or pointers. Its consuming CPU-unmap operation cannot discharge an
uncertain kernel DMA pin or authorize backing reuse.



\section{Transfer guarantees and limits}

\begin{enumerate}
    \item Page transfer without payload copying: for aligned,
        page-backed objects, ownership can move by changing mappings rather than
        copying bytes. Whether this is faster depends on payload size and
        mapping/TLB costs.

    \item Cross-domain stale access is constrained by mappings:
        when a memory object is moved, the sender's mappings are removed. Any
        later access through those mappings faults. When a borrow is revoked,
        the borrower's mappings are removed. This does not rule out bugs in
        unsafe code, page-table maintenance, or DMA.

    \item Borrows have defined lifetimes: a borrow is always tied to an
        IPC call. When the call completes (reply, cancellation, or server
        death), the borrow ends. A wait timeout alone does not cancel the call
        or end its loan; explicit cancellation is needed before reusing the
        borrowed storage. There is no ``I forgot to return it.''

    \item DMA ownership is tracked on the reference platforms: AArch64
        SMMUv3 and x86-64 VT-d/AMD-Vi pin mapped memory and restrict each
        requester to its DMA domain. The ownership-aware Rust API prevents
        ordinary CPU mappings from overlapping a transfer; raw coherent-ring
        implementations remain responsible for volatile/atomic access and the
        device protocol.

    \item Page tables enforce access. With correct MMU setup and TLB maintenance,
        unmapped CPU pages remain inaccessible even when a program uses unsafe
        code or C FFI, or contains a compiler bug. The implemented SMMUv3, VT-d,
        and AMD-Vi paths provide the corresponding DMA boundary for explicitly
        mapped objects.
\end{enumerate}
