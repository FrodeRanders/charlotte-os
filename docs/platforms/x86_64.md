# x86_64 Platform Status

> Status of the x86_64 port of Catten, its verified parity scope, and a
> precise map of the remaining platform-specific work. The AArch64 port is the
> original mature platform (boots,
> passes all self-tests, runs userspace at EL0 with a working syscall). x86_64
> now boots to ring 3 and runs the shared userspace service stack: name and
> object storage, Raft, service management and live upgrade, virtio-net/E1000E,
> discovery and distributed DNS, smoltcp TCP/IP, the HTTP state keyhole, and
> signed cluster deployment, migration, and dynamic membership.
>
> Boot with: `scripts/run-x86_64.sh` (QEMU q35, TCG, `-cpu max`, serial to
> `/tmp/charlotte-x86-serial.log`).
> On an x86-64 Linux host with accessible `/dev/kvm`, pass `--kvm` to use the
> host CPU through KVM. The Justfile's `qemu-run-x86_64` recipe selects it.
>
> A two-disk VMware appliance is also available. Its UEFI, NVMe, VT-d,
> persistent-storage, node-local service, and E1000E Ethernet paths are
> qualified under Fusion. See the
> [VMware appliance guide](vmware-x86_64.md).

## What works now

1. **Boot via Limine** — the kernel image loads and `bsp_main` runs.
2. **Serial console** (`log/serial_x86.rs`) — a 16550 UART driver on COM1
   (port `0x3F8`). Wired into `early_log!`/`early_logln!`/`_write_args`. Before
   this, x86_64 headless boot was completely silent (output was discarded).
3. **CPU feature requirement** — the kernel uses `RDTSCP` (for `get_lp_id` via
   `TSC_AUX`) and `WRFSBASE`/`WRGSBASE` (`init_lp_state`). These require a CPU
   model that supports them. `-cpu qemu64` does **not**; `-cpu max` does. The
   boot script uses `-cpu max`, and startup now checks RDTSCP, FSGSBASE, and
   SMEP explicitly before enabling the x86 execution path.
4. **Full boot + the registered self-tests pass.** x86_64 boots all the way
   through ISA init, physical memory, the kernel heap allocator, and all 16
   registered deferred self-tests. The shared coverage includes completion
   capabilities, syscall dispatch, IPI, ShardLocal, ShardMailbox, the CQ ring,
   endpoint IPC, blocking receives, cross-address-space IPC, memory
   move/borrow/copy/cancellation, cross-LP completion, ping-pong, and device
   capabilities. The device test uses an allocated MSI and live self-IPI on
   x86_64 in place of AArch64's synthetic GIC SPI.
5. **Per-LP APIC timer ownership** — every logical processor has an independent,
   lazily initialized timer state. Its owning LP performs calibration and local
   x2APIC setup on first use; timer state is no longer aliased through clones of
   one `Arc` created by the bootstrap processor.
6. **Multi-LP bring-up** — the kernel boots with `-smp 2`/`-smp 4`: secondary
   LPs enter through Limine, build their per-LP GDT/TSS/IDT, and join the
   scheduler. The scheduler-lifecycle verifier's cross-LP remote-abort
   regression passes.
7. **Ring-3 execution and the SYSCALL ABI** — user threads enter ring 3 via
   `iretq`, run hand-written stubs, and trap back through the `SYSCALL`
   instruction into the shared syscall dispatch table. The raw-syscall tests
   exercise the same IPC and cross-LP semantics as their AArch64 counterparts
   (`SELFTEST COMPLETE: passed=15 failed=0 pending=0`).
8. **Isolated user address spaces** — `AddressSpace::new_user()` builds a
   separate PML4 with the kernel's higher-half mappings copied, so ring-3 code
   only reaches what the loader explicitly maps. Context switches reload CR3,
   which (without PCID) flushes non-global translations.
9. **Rust EL0 services** — the `catten-syscall` x86 wrappers and the ELF
   loader are architecture-neutral, and `scripts/run-x86_64.sh --el0-smoke`
   builds, signs, and runs a real Rust-compiled `smoke` service at ring 3
   (`[el0 smoke] SUCCESS: x86_64 Rust ELF ran at ring 3 and wrote the sentinel.`),
   exercising the full `catten-rt` startup path and the syscall ABI from Rust.

## RESOLVED: heap #GP (was "bug A") — LA57 / paging-mode mismatch

**Symptom:** a #GP with `RAX = 0xff90000000000000` (non-canonical under 4-level
paging) during kernel-heap large-page mapping.

**Root cause:** `CpuInfo::get_vaddr_sig_bits()` read the CPU's *maximum* linear
address width from CPUID `0x80000008` EAX[15:8]. With `-cpu max` that is **57**
(the CPU supports 5-level paging / LA57). The kernel then selected
`LA_MAP_57BIT`, whose `kernel_allocator_arena` base is `0xff90000000000000` —
canonical only under 5-level paging. But Limine boots with **4-level** paging
(48-bit VAs), under which that address is non-canonical → #GP on first
dereference.

**Fix:** `get_vaddr_sig_bits()` now reports the width of the *active* paging
mode, derived from `CR4.LA57` (bit 12): set ⇒ 57, clear ⇒ 48. This selects
`LA_MAP_48BIT` under Limine's 4-level paging, so all kernel VAs are canonical.

## RESOLVED: silent triple-fault on any fault (was "bug B")

**Root cause:** the panic handler used `logln!`, which routes through
`INT_STATE` — a `LazyLock` whose first-use initialization **allocates from the
kernel heap** (`alloc::vec!`). When a fault occurred before the heap was ready
(or *because* the memory subsystem faulted), the panic handler's `logln!`
triggered a heap access → another fault → re-entered the panic handler →
infinite recursion → stack overflow → triple fault (silent hang).

This masked *every* early fault as a silent hang and was why the heap fault
looked like a mysterious lockup.

**Fix:** the panic handler now uses `early_logln!` (direct serial writes, no
heap, no `INT_STATE`). Verified: a deliberate page fault now prints
`Page fault at RIP=… faulting address=…` and exception delivery + the #PF/#GP
handlers all work correctly. Exception delivery was **never** broken.

## Resolved issues from the ring-3 / SYSCALL bring-up

- **SYSCALL GS base and stack switch** — `IA32_KERNEL_GS_BASE` points at the
  per-LP data area. Entry uses `swapgs` and switches to the per-thread kernel
  stack before its first write, so a user-controlled RSP can never redirect a
  supervisor-mode register save. Once that frame is safe, entry re-enables
  interrupts so timers and TLB-shootdown IPIs can preempt syscall dispatch;
  return masks them around `swapgs` + `iretq` and restores the userspace GS
  base.
- **SYSRET GDT ordering** — the GDT is `[null, kcode, kdata, ucode, udata, tss]`,
  which cannot satisfy `SYSRET`. Return to ring 3 uses `IRETQ` (works with any
  GDT layout), matching `user_trampoline`.
- **Kernel stack selection** — `TSS.RSP0` (and the per-LP `kernel_stack` slot)
  is set to the incoming thread's kernel stack top at every context switch, so
  ring-3 interrupts and syscall entry land on the correct per-thread stack.
- **Intermediate page-table permissions** — an intermediate PML4/PDPT/PD entry
  was created with the flags of the first page mapped beneath it and never
  widened, so a read-only code page mapped first would silently make later
  writable mappings read-only (effective W is the AND of every level). The
  walker now widens W/U on reused intermediate entries.
- **`map_existing_page` zeroing** — x86 fell back to the zeroing `map_page` for
  memory-object moves, clobbering live object data. A non-zeroing
  `map_existing_page` walk is now implemented.
- **Runtime rebalance** — `maybe_sample_rebalance()` was AArch64-gated and the
  x86 yield path never called it, so certified-migration sampling stalled. It
  is now architecture-neutral and wired into x86 `cond_yield_lp`.
- **Synchronous TLB shootdowns** — the x86 sync-IPI path was a placeholder. The
  rendezvous is now implemented: `send_sync_shootdown()` flushes the caller
  locally, interrupts every other LP (which reloads CR3), and spins on a barrier
  until all acknowledge. Initiators are serialized, generic invalidation IPIs
  stay local instead of recursively starting a rendezvous, and production
  memory-object, MMIO, and stack mapping boundaries issue their shootdowns only
  after releasing interrupt-masking locks. Contended spin locks also restore
  the caller's interrupt state while waiting, preventing the lock-holder / IPI
  acknowledgement cycle that previously stranded timer-blocked threads.

## Networking and cluster discovery

The virtio-net and E1000E drivers export the same `net0` frame protocol on
x86_64. An ordinary runner invocation attaches the selected controller,
acquires a DHCP lease, runs discovery and cluster services, and starts time
synchronization. `--no-network` disables that production path. `--net-test`
adds verification that reads the MAC and confirms hardware completion of a
transmitted frame:

```sh
./scripts/run-x86_64.sh release --net-test --timeout 60

# Exercise the VMware-compatible Intel 82574L model under QEMU:
./scripts/run-x86_64.sh release --net-test --nic e1000e --timeout 60
```

Two QEMU guests form a private Ethernet segment over QEMU's socket backend,
without TAP, root privileges, or vmnet. Start the listener first:

```sh
./scripts/run-x86_64.sh release \
  --instance node-a --mac 52:54:00:12:34:01 --net-listen 12000 --timeout 120
```

Then the second node in another terminal:

```sh
./scripts/run-x86_64.sh release \
  --instance node-b --mac 52:54:00:12:34:02 \
  --net-connect 127.0.0.1:12000 --timeout 120
```

Each guest broadcasts discovery probes through `net0`; the disco service on
each side learns the other and reports `discovered 1 peer(s)`. `--instance`
gives each VM independent boot media and serial logs
(`/tmp/charlotte-x86-node-a-serial.log` and
`/tmp/charlotte-x86-node-b-serial.log`). Add `--disco-test` only when the boot
should wait for and report this as a pass/fail verifier.

The storage transport is selectable independently of the network
(`--block nvme|ahci|virtio`, `--iommu intel|amd`), so a two-node run can also
exercise AHCI or virtio-blk behind either IOMMU.

The EFI image is disposable and attached as USB mass storage. The selected
NVMe/AHCI/virtio block device is a separate persistent image, so userspace
formatting and object-store writes cannot corrupt the next UEFI boot.

`--blank-storage` exercises the installable-disk path instead of host seeding.
The object store formats the blank disk and installs all missing signed x86-64
services from the kernel's immutable installation bundle. Existing valid
artifacts are retained on later boots. `--build-only` produces the boot and
data images without resolving QEMU firmware or starting the emulator; the
VMware appliance builder uses these two options.

### TCP/IP and HTTP

The shared smoltcp service and its frame-router adapter run unchanged on both
architectures. Two socket-linked x86-64 guests exchange TCP data with:

```sh
./scripts/run-x86_64.sh release --tcpip-test \
  --instance tcp-a --mac 52:54:00:12:34:56 \
  --net-listen 12001 --timeout 120

./scripts/run-x86_64.sh release --tcpip-test \
  --instance tcp-b --mac 52:54:00:12:34:57 \
  --net-connect 127.0.0.1:12001 --timeout 120
```

The HTTP keyhole runs over QEMU user networking. The runner forwards a host
port to guest TCP port 80, fetches the report, and verifies the HTTP request
counter in the returned JSON:

```sh
./scripts/run-x86_64.sh release --http-test --timeout 90

# Choose another host port when 8080 is occupied:
CATTEN_HTTP_HOST_PORT=18080 \
  ./scripts/run-x86_64.sh release --http-test --timeout 90
```

Opaque name-service registry keys in that report are represented as
`hex:<bytes>`; printable application and service names remain text.

### Cluster deployment and live upgrade

`--deploy-test` enables discovery, distributed DNS, `clusterctl`, signed
artifact upload and placement, cross-node invocation, migration and retirement,
and dynamic membership. Run it on both socket-linked guests, using four LPs:

```sh
./scripts/run-x86_64.sh release --deploy-test --smp 4 \
  --instance cluster-a --mac 52:54:00:12:34:01 \
  --net-listen 12002 --timeout 360

./scripts/run-x86_64.sh release --deploy-test --smp 4 \
  --instance cluster-b --mac 52:54:00:12:34:02 \
  --net-connect 127.0.0.1:12002 --timeout 360
```

The isolated persistent service-manager handoff is also available on x86-64:

```sh
./scripts/run-x86_64.sh release --live-upgrade-test --smp 4 --timeout 120
```

These suites have been qualified under QEMU TCG with four LPs. A two-LP full
deployment run can starve its progress threads under the current workload and
is not a supported qualification configuration.

## Known limitations

- **PCID is not enabled.** Address-space switches reload CR3, which flushes
  non-global translations. Cross-LP user TLB shootdowns conservatively reload
  CR3 on every target LP. This is correct without PCID; PCID allocation plus
  `INVPCID` is a future optimization.
- **SMAP is not enabled yet.** SMEP is enabled and syscall entry no longer
  touches the user stack. The remaining direct supervisor data accesses must be
  converted to explicit `STAC`/`CLAC` regions before enabling SMAP globally.
- **CPU feature fallback** — startup diagnoses missing RDTSCP, FSGSBASE, or
  SMEP, but there is no alternate implementation for older CPUs.
- **VT-d bridge scopes** — DMAR `INCLUDE_PCI_ALL` units and directly attached
  endpoint scopes are supported. Multi-hop PCI bridge scope paths are rejected
  until PCI bridge routing is represented in the topology model.
- **VMware network qualification** — E1000E initialization, protected DMA,
  link detection, and frame transmission are qualified under Fusion. The
  higher networking layers use the same `net0` protocol and are qualified with
  E1000E under paired QEMU guests, but paired VMware guests and bridged/host-only
  network configurations have not yet been exercised. VMXNET3 is not supported.
- **Architecture-specific programs** — the external Sitas test binary is still
  built only for AArch64, and the delegated PL011 UART test is necessarily
  AArch64-specific. x86-64 has a 16550 serial console with receive support for
  the shared `clusterctl` admin path, but no x86 Sitas artifact is built.

## Remaining work

1. **AMD-Vi MSI fault delivery** — the AMD-Vi driver drains its event log by
   polling; VT-d delivers faults through an MSI. AMD-Vi's fault MSI routes
   through its own PCI MSI capability (unlike VT-d's dedicated fault registers),
   so it needs a deferred post-topology MSI setup.
2. **Older-CPU compatibility** — provide fallbacks for the explicitly checked
   RDTSCP/FSGSBASE/SMEP requirements if hardware older than `-cpu max` is a
   target.
3. **PCID optimization** — enable `CR4.PCIDE`, assign recyclable PCIDs with a
   generation/flush discipline, and replace conservative CR3 shootdowns.
