# SEC-15: host key-file encoding

Date: 2026-10-20. Reviewed baseline: `3de9a8d`.

Generated key files now get one complete erasing hex-plus-newline buffer before
key bytes are copied. The [tracked evidence](evidence/2026-10-20-security-host-key-encoding.json)
records controls, source/artifact hashes and execution results. SEC-15 remains
**partial**, with **29 corrected / 6 partial / 3 open** overall.

## Finding and correction

`cluster-sign`'s `write_new_hex_key` previously called the generic `hex_encode`,
wrapped the returned string in `Zeroizing`, then appended a newline. Hex encoding
reserved exactly twice the key length; adding the newline caused one growth for
both 32-byte recipient keys and 64-byte signing keys. The final buffer already
erased on ordinary Drop. Growth could retire an earlier allocation beyond that
owner's reach, but the probes do not establish movement or inspect retired bytes.

The private `key_encoding::encode_key_file` helper now computes the complete
checked length, including the newline, before allocation. It constructs
`Zeroizing<String>` before writing, reserves once, and returns that owner.
`write_new_hex_key` borrows it through the same existing file creation/write
path. No additional key-file formatting or newline append remains at the caller.
The generic public identity/digest hex formatter retains its existing use.

Lowercase hex and one trailing LF are unchanged, as are command arguments,
private-file permissions, exclusive creation, rollback and output messages.
Public and private key files share this encoder. The input key stays borrowed
from its original owner. Size overflow rejects without copying, while ordinary
allocator/OOM behavior remains outside the guarantee. No dependency, wire,
persistent-record, cryptographic or kernel/userspace API change is introduced.

The existing [C18 row](../../reference/cleanup-recovery.md) records the host
byte owner. The previous writer already dropped its zeroizing final string in
this context; that release and the existing filesystem rollback policy remain.
Ordinary byte Drop adds no Charlotte capability/root cleanup, guards, waits,
remote teardown, registry, recovery custody or physical completion proof. The
manual source and signing/tool references now describe the complete record
reservation. The PDF is left untouched.

## Controls and host validation

Three baseline no-growth controls fail: 32-byte recipient output, 64-byte
signing output, and 64-byte output abandoned through a consumer error. Each
observes one allocation, one growth, one release and an erased final prefix.
A separate final-owner control passes. This preserves the distinction between
the existing final-buffer erasure and the growth gap.

The controls use an explicit byte adapter of the original private hex formatter
and the writer's wrap/append operations, replacing file I/O with a returned
owner. No baseline filesystem error or CLI execution is inferred from that
adapter. The allocator reads eight initialized public fixture bytes using
volatile accesses immediately before actual host deallocation. It reads no
freed storage, padding or uninitialized spare capacity. The selected allocation
is retired from observation after release. Reallocation counts do not prove
movement, retired-storage contents or physical erasure.

Four new byte tests cover 32/64-byte release without growth, abandonment,
same-address owner transfer and exact lowercase hex/newline bytes. The
[public all-byte fixture](../../../tools/cluster-sign/tests/fixtures/all-byte-key.hex)
is independently generated by Python's `bytes(range(256)).hex() + '\n'`.
Both baseline and corrected encoders match it. Corrected release assertions
observe one allocation, no growth, one release and an erased initialized prefix.
Original key inputs retain their own lifetimes.

A fifth test invokes the actual built CLI for `generate`,
`operations-signing-generate` and `operations-recipient-generate`. It verifies
private file length/syntax and mode 0600, absence of complete private text from
stdout/stderr, overwrite rejection with unchanged contents, and rollback of a
new private file when the public output already exists. Public output is
preserved. The test owns a uniquely created mode-0700 directory before cleanup.
Existing unit tests separately check key correspondence, restricted readers,
unsafe sources and signed control/trust-policy operations.

Debug tool tests pass **24 runtime tests**. Optimized tool/launch/Kafka/protocol/
S3/transport suites pass **222 runtime tests and 13 compile-fail doctests**.
Strict tool Clippy, workspace formatting and whitespace checks pass. The earlier
23-test debug run predates the actual CLI test; final runs identify all five new
cases. Expected baseline failures are retained separately from passing current
runs. No incidental corrected build/test failure was observed.
