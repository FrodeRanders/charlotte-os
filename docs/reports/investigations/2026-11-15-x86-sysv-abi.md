# X86 SysV/SSE2 runtime ABI 4 qualification

Work date: 15 November 2026. Baseline:
`b2bee95ff15929d175b335d3727fb46f14d412f5`. The
[earlier investigation](2026-11-15-x86-softfloat-future-incompatibility.md)
records the original compiler warning and isolated target comparison.

X86 userspace now uses the normal SysV/SSE2 ABI, without a red zone or a
soft-float variant. Runtime ABI 4 is the single current signed execution
contract. Nodes reject variants requiring ABI 1, 2 or 3; both architectures'
bundled applications and the Sitas test application were rebuilt and signed.
No persistent grammar, syscall number or integer register layout changed.

The [retained evidence](evidence/2026-11-15-x86-sysv-abi.json) contains compiler
identity, changed-code hashes, per-run kernel and signed-bundle identities,
native receipts, host results and separate failure outcomes. Temporary raw
logs and binary snapshots are not part of this published record; selected
diagnostics and their capture hashes are retained instead.

## Runtime boundary

The service target enables baseline SSE/SSE2 and removes the soft-float ABI.
The independent kernel target remains soft-float. Initial user function entry
reserves a zero return slot, giving `RSP % 16 == 8` as required by SysV C calls.
The native first-entry snapshot checks that alignment as well as zeroed GPR,
x87 and vector state in a fresh domain.

Returning syscall, timer, dynamic IRQ, IPI, exception and NMI stubs that enter
Rust retain their interrupted x87/XMM/MXCSR image in an aligned kernel-stack
frame. A shared assembly macro reserves 528 bytes after stack alignment,
performs FXSAVE64, and resets x87/MXCSR controls for kernel work. FXRSTOR64
restores the interrupted image before register/privilege return. Nested entries
and blocked syscall handlers keep separate images on their existing owning
stacks. This adds no allocation or capability owner. Normal thread kernel
stacks remain 64 KiB and the existing dedicated NMI stack remains 16 KiB.

Scheduled context switching retains its separate FXSAVE64/FXRSTOR64 contract,
including restoring the incoming image after callbacks. CR4.OSXSAVE remains
clear: AVX/XSAVE state is not admitted, and runtime crypto dispatch must respect
OS-enabled state. The existing software POLYVAL erasure selection remains
enabled for both x86 targets.

In regression builds only, syscall and timer handlers deliberately overwrite
XMM0--15 and reset x87 state. The raw user probe retains nondefault x87/MXCSR
controls and vector values across blocking and a monotonic 100 ms syscall loop.
It checks every XMM word, the x87 value/controls and MXCSR, while another domain
checks fresh-state clearing. The test hooks are absent from minimal kernels.
This makes the check discriminate actual preservation from handlers that happen
not to touch SIMD registers.

The signed service build no longer emits the soft-float/SIMD future warning.
The separate x86 kernel's rebuilt core/crypto graph still emits it. Strict
kernel builds pass today, but this remains an upstream/compiler compatibility
boundary; this change does not close it or suppress that diagnostic.

The manual was rebuilt in two passes, its SysV/SSE2 passage rendered and
visually checked, and current runtime-ABI descriptions updated. Historical
investigation and migration reports remain unchanged.

## Failed and nonqualifying attempts

An intermediate x86 guest before the initial-stack correction failed to reach
the registered verdict. Its captured kernel was
`f89f7ec670a25452d34df99d5638915ba831c34fce4a178faa64ca020da60196`.
The relevant diagnostics were:

```text
[+ 15.908004] FATAL USER FAULT: ASID=148 vector=13 error=0x0 RIP=VAddr(0x202a9) address=VAddr(0x0)
[+ 20.930499] [net] registration failed: ObservationTimeout
```

The source review separately identified and corrected the invalid initial SysV
stack alignment. The original instruction/register capture is not reproduced
here, so the observed fault is not assigned an instruction-level cause.

The combined Intel security + HTTP/TLS + DHCP run used kernel
`416f938ca314862b61b63931b869f2f7192111f814847cbf9f8ec98f0b9c15df`.
Its guest emitted the preservation/GCM receipts and:

```text
[+ 130.535362] SELFTEST COMPLETE: passed=19 failed=0 pending=0
TimeoutError: The read operation timed out
diagnostic result: reason=deadline, elapsed_seconds=180.00405479099982
runner result: guest failure/deadline captured
```

This is a failed combined runner result despite the guest verdict. The failure
capture also recorded a `host-probe-failed` request. Its relationship to load,
the kernel change or prior HTTP timing behavior is unresolved. The later
separate HTTP/TLS run passed with the existing deadlines, and the separate
AMD security run passed. Splitting these configurations establishes those
individual properties; it does not close or qualify the failed combined-load
case. No deadline was widened to turn that capture into a pass.

Preparation attempts also encountered a corrected test-helper syntax error,
a host Cargo invocation that inherited freestanding build-std configuration
and produced duplicate-core errors, a kernel Clippy invocation missing its
required bundle environment, and an ARM launch missing the rebuilt Sitas ELF.
Two signer tests could not bind sockets inside the sandbox, and the initial
TLS-control setup could not resolve crates.io there. Corrected inputs and
appropriately authorized runs passed; those setup failures are not native or
crypto acceptance evidence.

These are QEMU/compiler results, not physical-hardware, AVX, performance,
constant-time code-generation, production-trust or historical-incident closure
claims. The additional trap-frame CPU/stack cost has not been benchmarked.
