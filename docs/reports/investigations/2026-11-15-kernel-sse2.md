# X86 kernel SysV/SSE2 qualification

Work date: 15 November 2026. Baseline: `b340ce0f`. The
[userspace ABI-4 qualification](2026-11-15-x86-sysv-abi.md) established returning
trap-state preservation but retained a soft-float kernel target. This change
replaces that kernel target with the normal SysV/SSE2 ABI. Both current x86
targets now build without the former soft-float/SIMD incompatibility summary.
No dependency versions, public syscall registers or signed runtime-ABI number
changed. Runtime ABI 4 remains the single current execution contract.

The [retained evidence](evidence/2026-11-15-kernel-sse2.json) contains compiler,
target/source and kernel artifact identities, selected native receipts and
control outcomes. Complete temporary raw captures are not published. The
compiler remains `1.102.0-nightly` (`5f4effd579500175af844241eb179e756190f1e7`),
with LLVM 23.1.5, from `nightly-2026-11-14` on `aarch64-apple-darwin`.

## Required boot boundary

Compiled Rust can now use SSE2 in its prologue, copies and ordinary arithmetic.
The old late FP initialization inside ISA setup could not establish the
precondition for that earlier Rust code. The x86 ELF entry is therefore a raw
naked `_start`, and the Limine MP callback is the raw `x86_ap_entry`. Each:

1. Masks interrupts, clears DF and aligns the inherited kernel stack for C calls.
2. Calls `x86_boot_fp_init` before compiled Rust.
3. Calls the normal Rust BSP/AP body, preserving the AP's Limine argument.

The helper checks CPUID FXSR/SSE2 before executing FP instructions, clears
CR0.EM/TS, sets MP/NE and CR4.OSFXSR/OSXMMEXCPT, disables OSXSAVE, initializes
x87/MXCSR and clears XMM0--15. It allocates nothing. Unsupported baseline
hardware reaches a masked HLT loop before Rust or LP-backed factories. Later
`init_lp_state` owns TLS, SYSCALL and supervisor-protection setup; its old FP
fallback was removed.

The kernel retains its kernel code model, static relocation and no-red-zone
policy. Its existing FXSAVE/FXRSTOR thread and nested-entry ownership remains
active. AVX code generation rejects through a production compile guard because
the kernel does not own extended XSAVE state. The POLYVAL erasure flags and
destructor checks remain unchanged.

## Discriminating controls

Regression builds deliberately set EM/TS and disable OSFXSR/OSXMMEXCPT inside
the raw helper before normal setup. The first Rust BSP/AP checks verify the
normalized CR0/CR4 bits, default x87/MXCSR controls, and real generated f64
arithmetic. All four processors produced the recovery receipt in each native
regression configuration. Minimal images omit this fixture.

A kernel fixture holds an XMM15 sentinel for a bounded 100 ms interval without
calling Rust. Aligned loads of its LP's atomic timer-clobber counter occur
inside the assembly window, with LFENCE boundaries. It requires the caller's
IRQs already enabled, verifies actual local timer clobbers occurred and checks
the preserved value. It never enables an unknown caller mask. This supplements
the existing user probe for all sixteen XMM registers, x87 and MXCSR across
syscalls, IRQs and blocking. Timer counter instrumentation exists only with
`kernel_tests` and allocates no storage at runtime.

The real kernel/service compile controls accept C floating-point and SSE2
functions. An AVX-enabled control includes the production boot module and
rejects with:

```text
x86 kernel AVX code generation requires an extended-state ownership contract
```

Native entry checks require `_start`, `x86_ap_entry` and `x86_boot_fp_init` in
read-only executable sections and load segments. Disassembly confirms both raw
entries call FP initialization before their Rust body. A copy of the final
minimal ELF with its entry changed to `bsp_main` was rejected with:

```text
x86 ELF entry bypasses the raw FP initialization entry
```

The Intel security run preceded the addition of the test window's LFENCE
instructions; AMD and HTTP exercised the final measured window. That difference
affects test measurement, not production FP initialization or trap preservation.
All native configurations used the existing 180-second regression or 45-second
minimal budget. No kernel/service future-incompatibility summary occurred in
these builds. The old cached Cargo reports remain historical diagnostics.

No new runtime failure occurred in this kernel qualification. The prior failed
combined Intel security + HTTP deadline remains separately recorded in the
userspace report; these separate configurations do not close that incident.
The unsupported-CPU halt path was source/assembly reviewed, not exercised on
physical hardware lacking the required baseline. No AVX, physical-hardware,
performance, constant-time code-generation or production-trust claim is made.
